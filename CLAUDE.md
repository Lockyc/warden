# warden — agent orientation

## What warden is

warden is a **config-driven terminal multiplexer** — "curator for terminals." A single TOML file is the source of truth: it defines **windows** and the **project tabs** inside them. The app materializes itself from that config and **hot-reloads on save**. Each window carries a colour + title banner for at-a-glance identity; each tab is a real terminal opened in a working directory running an optional command. warden is **generic and content-agnostic** — it knows nothing about any specific tool; the command a tab runs is arbitrary (a shell, a TUI, an agent launcher, whatever).

Target platform: **macOS**. Linux is a *possible future consideration, not a guarantee* — the `warden-config` crate is kept platform-neutral (pure logic, no macOS-only APIs) so that door stays open, but nothing commits to shipping Linux. Not Windows.

## Current state — read this before assuming anything exists

Two layers are built:

- **Config-core** — the `warden-config` crate (pure logic, no GUI): parses/validates/resolves the TOML, diffs two configs for hot-reload, loads from disk, watches the file, ships a `warden validate` + `warden fmt` CLI.
- **GUI** — the `warden-app` crate: a config-driven, multi-window **macOS-only** Tauri app. What's built (README = the user-facing tour; [`docs/config.md`](docs/config.md) = the schema; [`docs/probing.md`](docs/probing.md) = presence probing; *Conventions & footguns* = the traps):
  - **A native window per `[[window]]`**, materialized at launch (gated by `open_on_start`), each with a colour + title banner and curator-style transparent chrome (Overlay titlebar, opaque draggable sidebar). Window size/position/maximized persist per Tauri label; sidebar width persists in `localStorage`.
  - **Tabs = embedded libghostty surfaces** behind the `TerminalSurface` seam, lazy-spawned on first focus (except `load_on_open`). Sectioned by `[[window.group]]` and auto-discovered from `[[window.root]]` project trees (`scanner.rs` → `synthesize_tabs`, rendered as a collapsible tree; rescan on open / hot-reload / manual refresh — no fs watcher).
  - **Tab-row dots:** live/cold (spawned?) doubling as an **unload** ✕ (kills surface+PTY → cold, respawns on next focus; unloading the visible tab leans **up** to a live neighbour, else a blank placeholder); amber **attention** badge on bell / OSC 9 / OSC 777 (decoded via `action_cb` → `notify.rs`; background tab badges, and a desktop-notify also raises a macOS banner via native `UNUserNotificationCenter` — **clicking the banner raises that window + selects the tab**); cyan **session-presence** dot (per-tab `probe`, off-main-thread scheduler) doubling as a **kill** (two-step confirm — `⏻` kills the session only and leaves the terminal live; `☠` kills the session **and** unloads the terminal in one action, via chrome-core's optional `onKillClose`) / **start** (types `cmd` into the live shell) toggle.
  - **Persistence & empty states:** warden is a **persistent app** — closing the last real window doesn't quit (⌘Q does). A single `sync_empty_surface` authority picks, whenever zero real windows are open, between the **launcher** (valid config with ≥1 window; lists every configured window, click to raise/reopen) and the **diagnostic** (no/invalid config; a mid-edit *parse* error instead keeps last-good windows up behind an error banner). Both are special non-counting windows (own label, invisible to `is_empty()`).
  - **Terminal affordances from libghostty's action stream** (`surface/ghostty.rs::action_cb`): **clickable links** — an `NSTrackingArea` forwards `mouseMoved`/`mouseExited` so libghostty can resolve the cell under the cursor (its link detection runs on that; without motion, URLs were wholly inert), then `MOUSE_SHAPE` drives the AppKit cursor via cursor rects (I-beam over cells, hand over a link) and `OPEN_URL` hands the clicked link to `NSWorkspace`. **Dead tabs** — `SHOW_CHILD_EXITED` unloads the tab back to **cold** (dot dark, focus the row to respawn) instead of leaving libghostty's "Process exited" overlay live forever; it reuses `Registry::unload`, so a process dying and a manual ✕/⌘W land the chrome in the same state (shared `applyUnloaded` in `index.html`, driven by `warden:tab-exited`).
  - **Hot-reload** is live (watcher + `reconcile` → per-window open/close/refresh; a window *title* change is destructive = close+open).
  - **App menu** (rebuilt on launch / window-set change / `tab_digit_keys` flip, with the `ManagerState` lock released): **Tab** (⌘⇧[ / ⌘⇧] cycle *loaded* tabs only; ⌘1–9 jump, or ⌘1/⌘2 cycle under `tab_digit_keys = "cycle"`; ⌘W unload, ⌘⇧W close window), **Config** (edit / reveal), **Window** (list + reopen; ⌘⇧T reopens the last closed).

Deferred (see [`docs/FOLLOWUPS.md`](docs/FOLLOWUPS.md)): ad-hoc `⌘T`/`⌘N` tabs; `TerminalSurface` seam hardening; FFI repr hardening (the action-tag discriminants); IPC hardening (a restrictive CSP ships; dropping `'unsafe-inline'` + reviewing `withGlobalTauri` remain); watcher debounce; argv passthrough.

## Intended architecture (where it's going)

- **Tauri** (Rust core + web chrome), one app, macOS-first. Tauri's cross-platform nature keeps a future Linux port viable, but macOS is the only committed target.
- **Windows = native macOS windows** — each `[[window]]` in config is one window (macOS `cmd+\`` cycles them), with its own colour + title banner. **Tabs = projects** within a window, cycled by a secondary keybinding. A single app/dock-icon by design — per-window identity is carried in-app via the banner, not via separate app bundles.
- **Terminal surface = embedded libghostty** behind a `TerminalSurface` seam — a small per-OS native shim hosts the surface (NSView on macOS; a GTK widget would host it on Linux if that port ever happens). A non-libghostty fallback impl (e.g. SwiftTerm-class) can sit behind the same seam. libghostty's embedding C API is officially unstable — **pin it** to a known commit.
- The `warden-config` crate is the foundation the app consumes (window/tab set, hot-reload reconcile, watcher).

## Workspace layout

Cargo workspace. `crates/warden-config` — the config crate (a library plus the `warden` CLI binary). Data flows one direction through small, independently-tested modules:

```
raw.rs       serde structs mirroring the TOML schema + parse()
  ↓
resolve.rs   validate + fill defaults + expand ~ → (Config, Vec<Warning>); ResolveError
  ↓
model.rs     clean resolved types: Config / Window / Tab / Warning
reconcile.rs reconcile(old, new) → Reconciliation (open/close windows, per-window colour/tab-add-remove/tab-reorder/set_meta relabel/respawn_tabs) for hot-reload
load.rs      load(path) = read+parse+resolve; config_path() (WARDEN_CONFIG override else ~/.config/warden/config.toml); LoadError
watch.rs     Watcher — notify-based parent-dir file watcher; fires load() on change
(fmt + colour live in the shared config-core crate — re-exported at warden-config's root as format_str/format_file + Colour/ColourError; the `warden fmt` subcommand itself delegates to config-core's shared `fmt_cli` — `bin/warden.rs` only resolves the default path — so `warden fmt` + `curator fmt` are one implementation, while `warden validate` stays here (warden's own schema); see Config formatting footgun)
bin/warden.rs  `warden validate [path]` + `warden fmt [--check] [path]` CLI
```

`crates/warden-app` — the macOS Tauri app that consumes the config crate. Key modules: `plan.rs` (config → `WindowSpec`/`TabPlan`, `reconcile` → `WindowOp`; `derive_tree_meta` computes each tab's tree/tree_path from the window's roots), `manager.rs` (`WindowManager`: materialize windows, apply reconciliations, diagnostic window; `effective_config` expands `[[window.root]]`s into synthesized tabs), `scanner.rs` (pure filesystem discovery of git projects under a root + `synthesize_tabs`; no AppKit/Tauri, unit-tests against temp dirs), `registry.rs` (per-window tab registry over surfaces), `surface/` + `ffi/` (the libghostty embed behind the `TerminalSurface` seam — macOS/objc2), `geometry.rs` (web-rect ↔ NSView-rect). `ui/index.html` is the chrome; `ui/diagnostic.html` the config-error page; `ui/launcher.html` the no-windows launcher.

## Config schema (`~/.config/warden/config.toml`; override with `WARDEN_CONFIG`)

**Full reference — every key, the cascade rules, and validation — is in [`docs/config.md`](docs/config.md); read it before touching config parsing/resolution.** In brief: the file has global defaults, then `[[window]]` blocks (native macOS windows) holding `[[window.tab]]` project terminals. Tabs can be sectioned by `[[window.group]]` (presentation only) or auto-discovered from a `[[window.root]]` scanned projects dir. `shell`/`cmd`/`probe`/`kill` **cascade** (global → window → tab, or root → window → global for discovered projects; nearest set level wins, `""` opts a level out). Load-bearing invariants that bite if forgotten:

- **`cmd` is typed *into* the shell, not exec'd** — it's libghostty `initial_input`, so a shell *function* like `amux` resolves and the shell survives the command exiting. Don't pass it as libghostty's `command`/exec target.
- **Tab identity is `id`-else-normalized-`dir`, never the title** (`Tab::key`); `title` is a pure, repeatable display label. Curated + discovered tabs share this dir-keyed scheme, so a curated tab **shadows** a same-dir discovered project.
- **Groups add no cascade level and roots add one** (root→window→global); both flatten to the single ordered `Tab` list with a `group` tag — the flat list is the only downstream shape.
- **Resolution collapses the cascade** to flat `Tab.shell`/`Tab.startup`/`Tab.probe`/`Tab.kill`; the app never sees the levels. `density`/`tab_digit_keys` are global, no cascade, unknown value → `ResolveError`.
- **Validation** errors on duplicate window title / tab identity / section name, empty required fields, bad colour, non-positive size, root `depth < 1`; a missing `dir` is a *warning* (created anyway). Invalid config is reported, never panics.

The probe **scheduler** internals (bursts, `PresenceCache`, the single-driver rule) live in [`docs/probing.md`](docs/probing.md); the config-adjacent traps (format-on-save, the probe/kill exec environment, tab-identity reconcile shapes) are in *Conventions & footguns* below.

## Build / test / run

- `cargo build` / `cargo test` (workspace). `warden-app` is macOS-only (libghostty embed); it fails to compile elsewhere by design.
- **Toolchain is pinned** in `rust-toolchain.toml` (currently `1.96.0`, with `rustfmt`+`clippy`) so formatting and lints are identical for everyone — an unpinned `stable` drifts and re-wraps committed code, which has bitten `just fmt`/`just check` here. rustup auto-installs the pinned version. **Keep it in lockstep with the shared crates — config-core, chrome-core, and shell-core — and with curator**: all three are *git dependencies* (chrome-core and shell-core also *build*-dependencies), so their own pins don't apply when warden builds them — warden's toolchain compiles the whole graph. Bump all of them together (curator's toolchain, and the config-core / chrome-core / shell-core revs), naturally when bumping a shared crate's pinned rev.
- `cargo run -p warden-config --bin warden -- validate [path]` — validates a config and prints the resolved window/tab tree + warnings (exit 0 ok / 1 load error / 2 usage).
- `cargo run -p warden-config --bin warden -- fmt [--check] [path]` — formats a config in the shared house style (config-core's taplo-backed formatter — no external taplo binary needed). `--check` is non-mutating and exits 1 if the file would change (for a pre-merge gate).
- `cargo run -p warden-app` — launch the GUI (reads `WARDEN_CONFIG` or `~/.config/warden/config.toml`).
- **`justfile`** wraps the common flows: `just run` (launches the app against `examples/config.toml` via `WARDEN_CONFIG`, so iterating never touches your real config), `just validate [path]`, `just test`, `just check`, `just fmt`, `just clippy`; bare `just` lists them.
- **`just hooks` — once per clone, or neither git hook exists.** `core.hooksPath` is per-clone *local* git config, so the repo cannot carry it: a fresh clone has **no** docgraph pre-push gate and **no** active-`[patch]` pre-commit guard until `just hooks` runs. Both are described elsewhere in this file as live safety nets — they are only live once switched on. `.github/workflows/ci.yml` runs the same fmt/clippy/test gate on push + PR to `main`/`dev` (macOS runner — `warden-app` compiles nowhere else), so CI is the backstop when a clone forgets.
- **Vendored libghostty** (`crates/warden-app/vendor/GhosttyKit.xcframework`, the terminal-surface embed) is Ghostty compiled from a **pinned, unmodified upstream commit** by [`lockyc/libghostty-build`](https://github.com/lockyc/libghostty-build) (its CI builds Ghostty's own `-Demit-xcframework` target on `macos-15` with Zig 0.15.2 — the runner-OS choice is what sidesteps the Zig-0.15.2-vs-macOS-26-SDK link failure), published as a release asset and pulled in via **`just revendor-ghostty`** (downloads the latest release, verifies its sha256, swaps `vendor/`). The universal `libghostty.a` is committed (~48MB, debug-stripped). The same release also carries libghostty's **runtime resources** (`vendor/resources/`), which warden must ship — see the terminfo footgun below. To move Ghostty versions: bump `GHOSTTY_REF` in libghostty-build → its CI republishes → `just revendor-ghostty` → update `vendor/PROVENANCE.md`. **Watch the FFI on a version jump:** libghostty's embedding C API is officially unstable, so after a bump diff `vendor/…/Headers/ghostty.h` against `ffi/mod.rs` — struct sizes are guarded by `const _` `size_of!` asserts that fail the build on drift (that's how the v1.3.1→main jump surfaced `ghostty_surface_config_s` shrinking 120→88 bytes when the host-managed IO backend was removed), but enum **discriminants** (the action tags) are *not* guarded, so eyeball those.
- **Packaging:** `just build` produces the release `warden.app` (needs the Tauri CLI — `cargo install tauri-cli --version ^2`); `just deploy` (now via `install.sh`) installs it to `/Applications` and relaunches. Release builds are **signed with Developer ID and notarized + stapled automatically** when the Apple signing/notary env vars are present in the build environment — `APPLE_SIGNING_IDENTITY` pointing at a Developer ID Application cert, plus `APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID` (or `APPLE_API_KEY`/`APPLE_API_ISSUER`/`APPLE_API_KEY_PATH`); Tauri runs the signing and `notarytool` submission (with hardened runtime) during `cargo tauri build`. With those vars unset (e.g. a contributor building from source), the build falls back to an ad-hoc/unsigned bundle, and `scripts/install-app.sh` strips the Gatekeeper quarantine xattr so a local copy runs either way. This is env-driven, not pinned in `tauri.conf.json`, so a build environment without the vars silently ships unsigned — set them to ship a distributable release. The bundle icon is `crates/warden-app/icons/icon.icns`, produced from the SVG masters by `assets/build-icons.sh`.
- **Releases:** the version is **single-sourced in `crates/warden-app/Cargo.toml`** — `tauri.conf.json` deliberately has **no `version` key** so the bundle inherits Cargo.toml's (don't re-add it; two version fields silently drift and the `.app` ships mislabelled). `warden-config` keeps its own independent version; the release tag tracks `warden-app`. Cutting a release (`main` tracks the latest release and is a clean ancestor of `dev`): on `dev`, bump `warden-app`'s version + refresh `Cargo.lock` → `chore(release): warden <v>` commit → `git tag v<v>` → fast-forward `main` to it → push `dev`, `main`, the tag → `gh release create v<v>` with notes summarising what shipped since the previous tag → **`just release`** (= `scripts/release.sh`) to build the notarized `warden.app`, `ditto`-zip it to `warden-<v>-macos.zip`, attach it, **and attach the updater artifacts** (`warden.app.tar.gz` + `.sig` + `latest.json`, via `scripts/gen-latest-json.sh`) so existing installs auto-update. `scripts/release.sh` reads the version from Cargo.toml and **refuses to run unsigned** (no `APPLE_SIGNING_IDENTITY` → exit) *and* without the updater key (no `TAURI_SIGNING_PRIVATE_KEY` → exit), so neither an un-notarized zip nor an unsignable/un-updatable release can masquerade as official. See *In-app updates* below for the updater key + endpoint.

- **In-app updates:** warden updates itself via `tauri-plugin-updater` (+ `tauri-plugin-process`), mirroring curator. **The self-updater is an app-agnostic capability owned by chrome-core** (see chrome-core's CLAUDE.md dividing-line decision — an updater is an *app* feature, not a terminal/browser one): the check + install/relaunch + the re-check cadence live there once so both apps inherit one implementation. warden's controller (`ui/index.html`) only passes its `auto_update` gate to chrome-core (`autoUpdate` in the mount config) and forwards the menu event to `sb.checkForUpdateNow()`; it keeps warden's updater *identity* (endpoint, pubkey, plugin registration) below. So chrome-core checks on launch **and re-checks every chrome-core `UPDATE_CHECK_INTERVAL_MS` (6h)** (warden is long-running, so a window open for days still surfaces a release) when `auto_update` is on, plus on **warden ▸ Check for Updates…** (always, via `warden:check-update` → `checkForUpdateNow()`); a hit shows chrome-core's update bar (with a × that dismisses for the session) and, on confirm, downloads + installs + relaunches — **confirm-to-install**. Endpoint (zero-server): `plugins.updater.endpoints` → `https://github.com/lockyc/warden/releases/latest/download/latest.json`. The updater verifies its **own** minisign signature (separate from the Apple cert) over `warden.app.tar.gz`; the private key lives at `~/.tauri/warden-updater.key` (never committed), its public key in `tauri.conf.json` (`plugins.updater.pubkey`). Cutting a release supplies the key to `scripts/release.sh` via `TAURI_SIGNING_PRIVATE_KEY` (contents/path of that file) + `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; the **password lives only in the vault today**, so each release currently needs a manual vault-unlock to hand it to the build env (a deferred improvement moves it to the macOS Keychain, sourced like `APPLE_PASSWORD` — see `docs/FOLLOWUPS.md`). **`createUpdaterArtifacts` is enabled release-only via `scripts/release.sh`'s `--config` override, NOT in the committed `tauri.conf.json`** (footgun: baking it in makes every `cargo tauri build` demand the signing key, breaking keyless `install.sh` / `just build` / `just deploy`) — so only the release build emits the signed tarball + `.sig`. The chrome is granted `updater:default` + `process:allow-restart` in `capabilities/default.json`. `darwin-aarch64` only (Apple Silicon). The **first** updater-capable release must be installed manually once (the bootstrap); every release after updates in-app. Unlike `density`/`sidebar_drag`, **`auto_update` is deliberately NOT wired into `main.rs`'s reload hook** (next footgun) — it's passed to chrome-core as `autoUpdate` once at init, and chrome-core arms both the launch check *and* the 6h re-check from it at that moment, so a hot-reload can't retroactively arm/disarm them on an already-open window: toggling `auto_update` takes effect next launch by design (restart-only), not because "nothing re-runs mid-session" — the periodic check does. Leave it out of the reload hook (it's not the "global-only won't hot-reload" bug).
- **Install from source:** `install.sh` (repo root) is the self-sufficient installer — `bash install.sh` from a checkout builds the current tree; `curl -fsSL https://raw.githubusercontent.com/lockyc/warden/main/install.sh | bash` clones/updates `~/.warden` and builds from it. Both backstop the Tauri CLI (`cargo install tauri-cli`), build via `cargo tauri build`, install to `/Applications/warden.app` (reusing `scripts/install-app.sh`), and seed `~/.config/warden/config.toml` if absent. `just deploy` delegates to `install.sh` (IN_REPO mode) then relaunches. The guided path is the **`/warden:install`** Claude command (`.claude/commands/warden/install.md`), which adds prerequisite checks and a config-edit/launch flow.

## Conventions & footguns (things that have bitten us / will bite again)

- **macOS app-icon safe area (the "our icon is bigger than everyone else's" bug):** Apple's icon grid sits the rounded tile in an **824×824 box centred on the 1024 canvas (~100px transparent margin each side)**. An edge-to-edge tile renders ~25% oversized in the Dock / cmd-Tab switcher next to every other app. `assets/icon-app.svg` deliberately draws the tile **edge-to-edge** (design it full-bleed); the margin is enforced in `assets/build-icons.sh`, which embeds the tile as a data: URI into an 824/1024 wrapper before rasterising — so the margin can't silently regress and the art never has to encode it. Do **not** "fix" this by making the SVG full-canvas again, and do **not** drop the wrapper. (This class of bug has recurred on every app; the script-level enforcement is the durable fix.)

- **A background window's surface must be seeded UNFOCUSED at spawn, or it renders at 60fps forever (the "cursor flashes around an unfocused window while Claude thinks" bug):** libghostty inits every surface `focus = 1` ("assume focused initially", `renderer/generic.zig`), which **starts its 60fps render display link** (`setFocus(true)` → `display_link.start()`; `setFocus(false)` stops it, dropping the surface to change-driven rendering only). warden otherwise clears focus **only** in `windowDidResignKey:` (a window that *was* key losing it) and the `performKeyEquivalent:` prev-surface handoff — **neither fires for a surface spawned in a window that was never key** (every background window at launch). Left focused, that background surface keeps rendering at 60fps and, while a TUI redraws, samples the text cursor at each intermediate cell tmux relays *between* redraws → the cursor visibly flashing around a background window. Ghostty.app never exhibits it because it derives focus from `NSApp.isActive && window.isKeyWindow` and sets it correctly; warden did not. **Fix (`surface/ghostty.rs::new`):** right after `set_surface`, seed focus from that same real state — `ghostty_surface_set_focus(surface, NSApplication::isActive() && window.isKeyWindow())` — so a background surface starts unfocused (display link stopped) and no longer samples the cursor mid-relay. The `windowDidBecomeKey:`/`windowDidResignKey:` observers keep it correct after spawn; this seeds only the initial state, which those observers structurally cannot (a never-key window emits neither). Don't drop this seed expecting the key observers to cover it, and treat 60fps CPU burn across idle background windows as this regressing. (The terminfo/`Sync` and tmux-`sync` work were chasing a *different* symptom — full-redraw tearing — not this; see the terminfo footgun below.)

- **warden MUST ship libghostty's terminfo, or every tab silently becomes a plain xterm (the `TERM=xterm-256color` / no-synchronized-output bug — full-redraw *tearing*, NOT the unfocused-cursor flash above):** libghostty decides what `TERM` to export by climbing from the running executable looking for the sentinel `Contents/Resources/terminfo/78/xterm-ghostty` (`resourcesdir.zig`). Find it → `TERM=xterm-ghostty` + `TERMINFO=<…>/Resources/terminfo`. Miss it → it *silently* falls back to **`TERM=xterm-256color`** (`termio/Exec.zig`; the only trace is a log line warden never surfaced). warden shipped no resources at all until this was found, so **every** terminal it ever opened was an `xterm-256color`. That is not cosmetic: `xterm-256color` advertises no `Sync` capability, so tmux never brackets its redraws in **DEC mode 2026 (synchronized output)** — the *one* signal that makes libghostty pause rendering (`renderer/generic.zig`: "If we're in a synchronized output state, we pause all rendering"). Unbracketed, the render thread can sample half-drawn frames during a *full-screen* redraw → visible tearing. (Enabling `Sync` needs a second half at the tmux layer — tmux does not derive the `sync` terminal-feature from the terminfo cap; agentmux sets it. And it only covers *full* redraws, not the small incremental updates a thinking agent emits — but that residue was never this footgun's flash; that was the focus bug above.) The fix is `vendor/resources/` (terminfo + shell-integration, from the same libghostty-build release as the `.a`), bundled by `tauri.conf.json`'s `bundle.resources` into `Contents/Resources/{terminfo,ghostty}`, plus `main.rs::configure_ghostty_resources` for the two ways this breaks: it **clears an inherited `GHOSTTY_RESOURCES_DIR`** (warden is routinely launched from inside another ghostty/warden terminal, which exports it — inherited, it would point warden at a *different* Ghostty build's terminfo; same reasoning as the `$TMUX` scrub) and, in **debug** builds only, points it at `vendor/resources/` since an unbundled `cargo run`/`just run` has no bundle to climb to (without which dev silently runs `xterm-256color`). Don't drop the bundled resources to slim the app, don't "simplify" the env handling away, and treat a `TERM` of `xterm-256color` inside a warden tab as this bug regressing — `echo $TERM` in a tab is the one-command check.
- **Never free a surface from inside `action_cb` — libghostty is still standing on it (the `SHOW_CHILD_EXITED` use-after-free):** `action_cb` is called *mid-function* by libghostty, which keeps using the surface after we return. `Surface.childExited` (Surface.zig) is the sharp case: once the apprt answers `true` it skips writing its "Process exited" text, then reads `self.config` and calls `self.close()` — on the surface we just handed back. warden's dead-tab handling unloads the tab, and unloading **frees the surface** (`Registry::unload` → `GhosttySurface::close` → `ghostty_surface_free`), so doing that synchronously inside the callback is a use-after-free. It reads as fine and *tests* as fine — a UAF on still-mapped memory doesn't crash — which is exactly the trap. So `action_cb` boxes the `ChildExited` event and `dispatch_async_f`s it onto the main queue: libghostty's stack unwinds, *then* warden tears the tab down (`emit_event_trampoline`). Bell/notification stay synchronous — they free nothing. Any future action whose handler could destroy a surface (or take the `ManagerState` lock, which a synchronously-raised action could otherwise deadlock against) must take the same deferred path; don't "simplify" it back to a direct `emit_surface_event`.
- **Raw-string test fixtures with a colour hex:** a Rust `r#"..."#` literal containing `colour = "#..."` self-terminates early at the `"#`. Use `r##"..."##` for any TOML test fixture that includes a hex colour. (Hit repeatedly across modules.)
- **The watcher matches the config file by file name, not full path** (`watch.rs`) — deliberately. This survives macOS FSEvents reporting `/private/var/...` vs a caller's `/var/...` symlink, and survives atomic-save editors that swap the file inode (the watch is on the parent dir). Do **not** "fix" it back to full-path equality, and do **not** add an `event.kind` filter — spec requires firing on *any* event for the file (atomic-save renames can surface as `Create`).
- **Format-on-save rewrites the user's config but can't loop the watcher** (config-core's `format_file` + `main.rs` reload hook): when `format_on_save` is set, a clean reload calls `format_file`, which rewrites the file **only if the formatted bytes differ** (diff-guard) and **atomically** (temp file in the same dir + rename). warden's own write retriggers the watcher once, but the now-formatted file is byte-identical → no write → it settles. Two invariants hold this together — don't break them: formatting must stay **idempotent** (so the guard converges), and the hook runs **only on the clean-parse branch** (never rewrite a mid-edit-broken file; that path keeps last-good + shows the error banner). The house style lives in config-core's `format_str` (taplo `indent_tables`/`indent_entries`/`align_entries`/`align_comments`, `reorder_keys=false`, `allowed_blank_lines=1`, LF + trailing newline) plus a `separate_sections` post-pass that puts **one blank line before each container section** (`[[window]]`, `[[window.group]]`) while keeping **nested tabs tight** (no blank before a `[[…tab]]`) — taplo can only *cap* blank lines, so the pass both inserts the container separators and strips blanks that crept in before a tab. Tight-vs-separated keys on the header's leaf segment (`tab` = tight). - **Tab identity is `id`-else-`dir`, never the title** (`Tab::key`, `resolve.rs`): a tab's explicit `id` if set (trimmed, non-empty — `id = ""` counts as unset), else its normalized `dir` (`normalize_dir_key`) — unique window-wide across loose + grouped **curated** tabs. A discovered `[[window.root]]` project uses the same dir-keyed scheme via its absolute path (see [`docs/config.md`](docs/config.md) for how that lets a curated tab shadow a same-dir discovery). `reconcile` diffs windows by `title` and tabs by this key. **`title` is a pure, repeatable display label** — not part of identity, not deduplicated, and relabels live: a kept tab's `title` change (along with `group`/`probe`/`kill`) rides `WindowUpdate.set_meta` and applies without respawning — sidebar re-render/re-section, new probe/kill commands on the next poll/kill, new title on the row immediately. A kept tab's **terminal-spec** change — `dir`, `cmd`, `shell`, or `load_on_open` — rides the sibling `respawn_tabs` path: `warden-app` tears down and respawns that one tab's PTY in place with the new spec (a terminal can't migrate its cwd/session, so this is a targeted in-place respawn, not a reopen-on-next-focus or a wait-for-restart). A window **title change** is destructive: it appears as close(old)+open(new), killing and recreating that window's terminals (including `load_on_open` ones).
- **`rescan_root` diffs a fresh scan against what's on screen, not two scans against each other.** The tempting-but-wrong shape is to scan the root, wait, scan it again, and diff those two scans to find what changed on disk. The actual command (`main.rs::rescan_root`) instead re-expands `raw_config` through `manager::effective_config` once and runs `warden_config::reconcile(&m.last_good, &fresh)` — i.e. it diffs the **new** scan against `last_good` (the config already reflected on screen), the identical shape a hot-reload uses. This correctly captures drift from *any* source since the sidebar was last updated (a prior rescan, a hot-reload, the initial open), not just filesystem changes since some earlier throwaway scan — a double-fresh-scan diff would miss anything the screen hadn't caught up to yet. Don't "simplify" this to comparing two scans directly.
- **Window size/position restore is per-label and runtime-triggered** (`tauri-plugin-window-state`): the plugin saves automatically on close/exit, but its *automatic* restore only fires for windows declared in `tauri.conf.json` — warden builds every window at runtime, so `manager.rs::build_window` must call `window.restore_state(SIZE|POSITION|MAXIMIZED)` itself right after `.build()`. - **App-menu shortcuts vs libghostty keybinds (the "tab hotkey only sometimes works" bug):** macOS sends a ⌘-combo to the key window's view hierarchy `performKeyEquivalent:` **before** the main menu, and libghostty has its *own* built-in keybinds for the standard tab chords (`⌘⇧[`/`⌘⇧]` = prev/next tab, `⌘1–9` = goto-tab — chords warden's Tab menu also binds; under `tab_digit_keys = "cycle"` warden instead maps `⌘1`/`⌘2` to next/prev and `⌘3–9` to jump). So if `WardenHostView::performKeyEquivalent:` forwards a chord to libghostty first, libghostty matches its keybind, returns *consumed = true*, the view returns `YES`, and the event is swallowed before warden's menu item ever fires. The fix (in `surface/ghostty.rs`): give the **main menu first refusal** — `NSApplication::sharedApplication().mainMenu().performKeyEquivalent(event)` at the top of `performKeyEquivalent:`; if it returns true the menu owns the chord, so stop. Only forward to libghostty when the menu declines. The menu's own accelerators define the reserved set, so it self-maintains — but don't "simplify" by forwarding to libghostty first, and remember any new menu accelerator automatically wins over a colliding ghostty keybind (that's intended). **One chord is reserved without being a menu accelerator: `⌘\`` / `⌘⇧\`` (macOS's own "cycle windows of this app").** `performKeyEquivalent:` short-circuits it (via `is_window_cycle_chord`, matched by physical grave keycode so it's layout-independent) and returns `NO` **without forwarding to libghostty** — otherwise a surface in the Kitty keyboard protocol (a running TUI turns it on) encodes `⌘\`` to the PTY and reports *consumed = true*, so warden returned `YES` and AppKit's cycling never ran — the chord died silently on whatever tab had such a program running while bare-shell tabs cycled fine (the "cmd+\` only works on some tabs" bug). warden owns **no** cmd+` binding of its own by design: window cycling is macOS's and fighting it would be a losing battle — the reservation just keeps the terminal from eating it. Don't "fix" this by adding a warden cmd+` handler or by dropping the reservation so it forwards again.
- **libghostty cursor focus must track AppKit's first responder (the "cursor isn't filled but still types" bug):** libghostty draws a *filled* block cursor only while it believes the surface is focused (`ghostty_surface_set_focus(surface, true)`), a *hollow* one otherwise. Focus was pushed in only two paths — `GhosttySurface::focus()` (tab activate, via `makeFirstResponder`) and `performKeyEquivalent:` (⌘-chords, which sets the previous surface false). A plain **mouse-click into a terminal** makes the view first responder via AppKit directly, so `keyDown:` routes there (typing works) but nothing told libghostty — if another surface had grabbed focus via a chord, this one stayed false and rendered a hollow cursor while accepting input. Fix (in `surface/ghostty.rs`): a `becomeFirstResponder` override pushes `ghostty_surface_set_focus(true)` + retargets `FOCUSED_SURFACE` — that's the AppKit hook every first-responder *change* funnels through (click, `makeFirstResponder`), so the cursor tracks the real first responder. Don't drop it expecting `focus()`/`performKeyEquivalent:` to cover the click path — they don't. `becomeFirstResponder:` does **not** fire when a window merely re-becomes key with its old first responder intact, so it alone left the inverse glitch (filled cursor in a *non-key* window, or stale-hollow after the window returns). That's closed by per-window **`windowDidBecomeKey:`/`windowDidResignKey:`** observers (registered in `new`, scoped `object: window`, removed in `close`) that flip the active tab's focus flag with key state — gated on `!isHidden()` so only the keyed window's visible surface reacts (every tab view hears the notification; one is unhidden). The two mechanisms are complementary: first-responder for *which surface within a window*, key-state for *which window* — don't drop either.
- **The render layer's `contentsScale` must track the backing scale (the "terminal is scaled wrong after unplugging a monitor" bug):** libghostty's macOS renderer makes warden's `WardenHostView` **layer-hosting** — it assigns its own render layer to the view's `layer` and sets that layer's **`contentsScale` only at creation** (`renderer/Metal.zig`). Its live content-scale path (`ghostty_surface_set_content_scale` → `contentScaleCallback`) reflows font/cell metrics + framebuffer but **never touches the layer's `contentsScale`**. So when the window moves to a different-DPI display, Core Animation keeps compositing the layer at the *stale* scale and magnifies/shrinks the whole surface — even though the font itself reflowed. **The fix** (in the `viewDidChangeBackingProperties` override, `surface/ghostty.rs`): push `window.backingScaleFactor()` onto `self.layer`'s `contentsScale` ourselves, inside a `CATransaction` with actions disabled (so CA doesn't animate the change) — the same fix Ghostty.app's own `SurfaceView` uses. Session-preserving (no surface restart), runs unconditionally. Still push content-scale + size together via `apply_surface_geometry()` (font reflow + framebuffer) — the `contentsScale` line is purely the *compositor's* scale, orthogonal to those. **If a DPI change ever looks wrong again, the lever is the layer scale — not the font path (it does reflow) and not respawning the surface (a removed dead end).** **Sibling multi-monitor concern — vsync/refresh, handled separately via `ghostty_surface_set_display_id`:** the `contentsScale` fix above is the *compositor scale*; libghostty's render display link also needs the *display's* `CGDirectDisplayID` so vsync tracks the right monitor's refresh rate (a window moved to a mixed-refresh second display otherwise keeps the creation display's link → judder / wasted frames). warden sets it (`window_display_id` → `deviceDescription["NSScreenNumber"]`, same source as Ghostty.app) at spawn **and** in a `windowDidChangeScreen:` observer — a screen move that also changes scale is covered by `viewDidChangeBackingProperties`, but a same-scale move to a different-refresh display fires *only* `windowDidChangeScreen:`, so both hooks are needed. Don't drop the display-id seed/observer expecting the backing-properties path to cover refresh — it only covers scale.

- **A surface that fails to spawn degrades to a cold tab — never `.expect()`/`unwrap()` it (the "one bad tab crashes the whole app at launch" bug):** `GhosttySurface::new` returns `Result`, and `Registry::add` / `ensure_spawned` / `activate` propagate it (`registry.rs`). - **A new *global* config setting won't hot-reload if you only thread it through the per-window DTO (the "density-only edit does nothing" bug):** `reconcile` diffs *windows/tabs*, and `apply()` emits `warden:refresh` **only for windows with a per-window diff** (colour / tab add-remove / order / `set_meta`). A global setting changed *alone* — `density`/`sidebar_drag`, like the menu's `tab_digit_keys` — produces an **empty reconcile**, so no refresh is emitted and the chrome never sees it. - **`emit_to` leaks to sibling webviews — per-window events must carry a `label` and the chrome must filter on it (the "both windows respond to one hotkey" bug):** with the global `listen` (`window.__TAURI__.event.listen`), `app.emit_to(label, …)` does **not** restrict delivery to that one window's webview — every window's listener receives the event. - **Session-presence probing: the scheduler is the single driver — full internals in [`docs/probing.md`](docs/probing.md).** The load-bearing rules a change here must not break: probes run **off the main thread** (snapshot under the `ManagerState` lock, release it before `sh -c`); a window's tabs are probed **concurrently on a bounded pool** (`sweep`, capped at `MAX_PROBE_CONCURRENCY`) so a wide `[[window.root]]`'s pass is ~`ceil(tabs/concurrency)` probe times not the O(tabs) *sum* — **don't serialize it back** (that was the "dot takes ages to clear after kill" lag); every trigger `bump`s a window into a fast burst and **nothing calls `probe_window`/`run_probe` directly or adds a one-shot reprobe** — a tab-specific trigger (kill/start/activate) uses `bump_tab`, which probes **that tab first** (`order_work`) so its dot lands in the first wave (ordering, *not* a reprobe); `run_scheduler` is spawned **exactly once** (a second one busy-spins on a disconnected channel → wedged core, not a quiet extra poll); emits are **per-tab, changed-only, `label`-stamped + `forMe()`-filtered** (never a batched end-of-pass emit); the persistent **`PresenceCache`** paints dots on the first render of a (re)opened window (seeded into `init_dto` at build), so **don't tie it to the Registry or clear it on window close**; **`probe_now` replays `PresenceCache::snapshot` to the chrome the instant its listener is ready** — the first probe pass can finish in the build→listener gap, dropping its emits with `prev` then populated so nothing re-emits (a session that pre-existed launch → dot stuck dark; this is the "launchpad dot never lights after deploy" bug the concurrent sweep surfaced), so **don't drop that replay** expecting the live burst to cover first-paint; the replay only works because each result is written to the cache **per tab, before its emit** (`observe`) — batching the write at the *end* of the pass leaves a wide window's in-flight sweep dropping early emits while the replay still reads an empty cache, latching those dots dark for the life of the process (the "my amux session is live but the dot is off" bug), so **don't move the record back to end-of-pass**; `{dir}`/`{title}` are substituted **raw**, so quote them. `probe_interval = 0` is event-driven-then-idle, not "no probing". See `docs/probing.md` for the mechanism behind each.
- **Never add an optimistic dot-clear on kill — it reintroduces the kill-dot flicker (off→on→off).** The presence dot tracks `warden:session-state` alone with **no optimistic clear**, so it only shows real probe results, which move present→absent **monotonically** as the kill lands. Two facts keep it flicker-free: `kill_session` runs the kill to completion *before* bumping the scheduler (`main.rs`), so the first post-kill probe already reflects final truth; and with no optimistic clear there's no prematurely-dropped dot for a stale mid-teardown pass to "undo". - **The default shell is your login shell (absolute, run as login) — warden is a terminal, so it behaves like one (`warden-app`'s `login_shell()`).** When no `shell` is set at any cascade level, warden defaults to `$SHELL` (fallback `/bin/zsh`) with `-l` appended — read in `warden-app`/the CLI binary (NOT the pure `warden-config` crate, which takes the default as data via `resolve_with`/`load_with`/`Watcher::with_default`; the bare `resolve`/`load` keep `DEFAULT_SHELL` for tests). `$SHELL` is an **absolute path** (launchd sets it from the user's directory record even on a Dock/Finder launch), so libghostty finds the shell without any PATH lookup — sidestepping the GUI-launch minimal-PATH trap *by construction*, the way Terminal.app/iTerm/Ghostty do — and `-l` makes it a login shell that sources config and builds PATH for the session. - **A GUI launch hides your PATH — warden imports the login-shell PATH at startup (`main.rs::restore_login_path`):** a `.app` opened from Dock/Finder/Spotlight inherits only the minimal launchd PATH (`/usr/bin:/bin:/usr/sbin:/sbin`), so a command named by **bare command** — a config `shell = "fish -l"`, a bare `tmux` in a `probe` — is `exec: … not found` and silently fails (the shell dies on spawn, symptom: a tab that only ever shows "Process exited. Keep it in the app shell, not chrome-core (the mark differs per app, and it's a content-area concern, not a sidebar one). It must stay **opaque** (the window is transparent; a non-opaque fill leaks the wallpaper — the exact leak it exists to stop), and the toggle stays gated on `active` so it can't bleed through a translucent terminal theme. The shield SVG is hand-recoloured from `assets/icon-app.svg`'s path geometry (muted grey, no tile/gradient) — if the app mark changes, re-derive it from the same source.
- **Every libghostty surface's render layer must carry an OPAQUE background, or clicking a *cold* tab flashes the wallpaper (`GhosttySurface::new`):** libghostty makes the host view layer-hosting and (when embedded) sets the layer's `contentsScale` but **not** its `backgroundColor` — setting the background is the embedder's job, exactly as Ghostty.app's own `SurfaceView` does. Left unset, the render layer is transparent until Metal presents its first frame, so a freshly-spawned surface shows the transparent window hole (the desktop) for those frames. Activating a cold tab hits this: `activate()` hides the old (opaque, covering) surface and shows the new one *before* it has painted, and the `#empty-state` placeholder can't win that sub-frame race — it toggles `display`, and its webview composite loses to the native surface swap on both edges (old-surface-hide before the placeholder paints; placeholder-hide on `activate_tab`'s return before the new surface's first paint). So `new` sets `host_view.layer().backgroundColor` to an opaque `#0e1516` (matching the `#empty-state` backstop) right after `ghostty_surface_new` — once painted, libghostty's drawable covers it, so a normal terminal looks identical; it only fills the un-painted gap. The colour goes through a properly-encoded `CGColor` type (a bare `*mut AnyObject` fails objc2's msg_send type-check: `expected ^{CGColor=}, found @`). Don't drop it to "simplify" — the placeholder is not a substitute (it can't cover the transient), and don't set the layer opaque expecting the *terminal* to be opaque (it's about the pre-first-paint frame, not steady state).
- **The `#sidebar` wrapper's `data-tauri-drag-region` is NOT inert — it drags the title-bar inset (the "title bar stopped moving the window" bug):** `index.html`'s `#sidebar` has `padding-top: 28px` to clear the traffic lights, and gets `.cc-root`'s opaque background — so that 28px strip *is* the native title-bar zone, painted, and part of the `#sidebar` element. chrome-core's `windowDrag` stamps the banner / tab-list / group-headers (the sidebar **body**, toggled by `sidebar_drag`), but those cover only the content box; the banner sits *below* the padding. So the inset's only drag handle is the attr on `#sidebar` itself, and a mousedown there targets `#sidebar` (padding is part of the element, no child on top). It *looks* removable — "the children cover the wrapper, so this attr does nothing" — and removing it once (in the sidebar_drag commit) is exactly what killed title-bar dragging while leaving body dragging working, so the app *seemed* fine. It's intentionally **always-on** (a macOS title bar always moves the window) and independent of `sidebar_drag`; because the banner + `flex:1` tab-list fill the content box, it only ever catches the 28px inset, so the toggle still owns the body. Don't drop it.
- **Keep the migration complete:** this is a young codebase; finish changes in-branch, no transitional fallbacks.
- **Stale frontend embed:** `tauri-build` (2.6.x) emits no `rerun-if-changed` for `frontendDist`, and the `ui/` assets are embedded at compile time via `generate_context!`. So after a *frontend-only* edit (`index.html`/`diagnostic.html`/`launcher.html`), `cargo run` silently serves the **stale** HTML until some Rust change forces a recompile. `crates/warden-app/build.rs` watches the **hand-written** assets (`cargo:rerun-if-changed=ui/index.html` + `ui/diagnostic.html` + `ui/launcher.html`) to defeat this — keep them, and add any new hand-written page to that list. It deliberately does **not** watch `ui/` broadly: build.rs itself writes the generated `ui/chrome-core.{css,js}` (materialized from the pinned chrome-core crate) into that dir, so a broad watch would self-trigger a rerun every build. If you edit the frontend and the change "doesn't take," suspect a stale embed (touch a `.rs` file or `cargo clean -p warden-app`). (`build.rs` also materializes the shared release scripts from the pinned **shell-core** crate and stamps the build via `shell_core::build_stamp()` — see the shell-core section below.)
- **A hot-reload while in the launcher state must reconcile, not re-materialize (the "closed windows reopen themselves on save" bug):** the reload hook's recovery branch keys on the **diagnostic window's presence** (`get_webview_window(DIAG_LABEL)`), NOT `is_empty()`. Both the diagnostic and the launcher states are `is_empty()` (zero *real* windows), but only the diagnostic state should re-materialize; the launcher state must take the reconcile path (unchanged config keeps user-closed windows closed; an added window opens and the launcher recedes). Keying on `is_empty()` would reopen every `open_on_start`-false / user-closed window on any save. Relatedly, the two error branches (parse error / no `[[window]]`) call `show_diagnostic` + `close_launcher` directly rather than `sync_empty_surface`, because on a parse error `last_good` still has windows, so `sync_empty_surface` would pick the launcher and hide the error — the diagnostic must win.

## Relationship to curator (the shared chrome-core component)

warden and **curator** ([github.com/Lockyc/curator](https://github.com/Lockyc/curator)) — a sibling public macOS Tauri app that curates **browser keeper-tabs** (webviews) where warden curates **terminals** (libghostty surfaces) — share the same sidebar chrome, extracted into **chrome-core** ([github.com/Lockyc/chrome-core](https://github.com/Lockyc/chrome-core)). Both apps consume it, so a look/behaviour change is made once and both move together.

- **The sidebar chrome IS chrome-core (the view) — change it there, not here.** chrome-core owns the banner + accent tint, grouped tab rows (letter tile, title, the three dot slots: attention / presence / live-unload), the kill-confirm row overlay, density tokens, the resize-drag, the error bar, and the **collapsible project-tree rendering** (`buildTree` + tree render: compressed single-child folder chains, expand/collapse state persisted in `localStorage`, a manual refresh control on the section header, an empty "No projects found" state) driven by each tab's `tree`/`treePath` DTO fields. It's a build-dependency pinned by `rev`; `build.rs` writes `SIDEBAR_CSS`/`SIDEBAR_JS` into `ui/chrome-core.{css,js}` (git-ignored) before `generate_context!` embeds them. `ui/index.html` is now a **page shell + thin controller**: the `#app`/`#terminal-hole`/empty-state topology, `reportRect`, the `forMe` per-window filter, the first-probe handshake, and a controller that maps the component's callbacks (`onSelect`→`activate_tab`, `onUnload`→`unload_tab`, `onKill`→`kill_session`, `onKillClose`→`kill_session` + `unload_tab`, `onStart`→`start_session`, `onRescan`→`rescan_root`, `onResize`→CSS width) and events (`warden:refresh`→`update`, `warden:notify`→`setAttention`, `warden:session-state`→`setPresence`, `warden:error*`→`setError`/`clearError`) to warden's backend.
- **What stays per-app is topology + backend, not the sidebar.** warden keeps its native-surface hole (`#terminal-hole` + `reportRect` + the empty-state placeholder) and its Tauri commands/events; curator keeps its content webviews + its own commands. These are the ~40-line controllers, not chrome duplication. warden feeds the component a normalized tab DTO where `presence` (probe), `killable` (kill), `startable` (has a `cmd` to restart a dead session), and `tree`/`treePath` (project-tree-roots sectioning) are warden-only — curator never sets them — and `attention` carries no count (curator's unread count does). warden also sets the window-level `windowDrag` flag (from its `sidebar_drag` config, default on) so the component makes the non-interactive chrome a `data-tauri-drag-region`; the component defaults it **on** when absent, so this is warden opting the toggle *in/out* rather than enabling a default-off feature. warden passes **no** `active` field, so the component owns selection (preserve + fall back to first, firing `onSelect` to activate); curator passes `active` because its Rust side is authoritative.
- **A new `TabDto` field is invisible to the chrome until `toComponentDto` forwards it (the "tree rendered flat" bug).** warden's Rust `TabDto` and the chrome-core component DTO are *separate shapes*; `ui/index.html`'s `toComponentDto` hand-maps one to the other. Adding a field to `TabDto` (Rust) is only half the wiring — if `toComponentDto` doesn't copy it across, the component simply never sees it, with no error. This is exactly how `tree`/`treePath` shipped inert: the Rust side emitted them and chrome-core rendered trees on `tree === true`, but the controller dropped both, so every `[[window.root]]` rendered as a flat group. When you add a component-facing tab field, add it to the `TabDto` struct **and** the `toComponentDto` mapping in the same change.
- **Dev iteration on the chrome behind a pinned rev is higher-friction — use the `chrome-*` just recipes** (they assume the sibling `../chrome-core` ghq checkout). **`just chrome-dev`** activates a normally-commented `[patch]` in the workspace `Cargo.toml` so warden builds against your local `../chrome-core` (uncommitted edits included); iterate, then **`just chrome-pin`** re-pins `crates/warden-app/Cargo.toml` to `../chrome-core`'s pushed HEAD and re-comments the patch. **config-core and shell-core have the mirror pairs** — **`just config-dev`** / **`just config-pin`** (re-pins `crates/warden-config/Cargo.toml`) and **`just shell-dev`** / **`just shell-pin`** (re-pins `crates/warden-app/Cargo.toml` — shell-core appears there twice, as a build-dep and a dep, and `shell-pin` re-pins both), since both are git-pinned the same way and hit the identical land-order footgun; the three cores use **scoped `#PATCH:chrome#` / `#PATCH:config#` / `#PATCH:shell#` sentinels** in the workspace `Cargo.toml` so each `*-dev` uncomments only its own patch. **Never commit an active patch** — a path patch builds green for you but is unresolvable for every clone/CI; **`just gate` refuses while any is active, and a `.githooks/pre-commit` guard blocks a commit that stages one** (the two safety nets). Edit chrome-core's `assets/sidebar.{css,js}` — never the generated `ui/chrome-core.*`. For **visual** tweaks, skip building warden entirely: chrome-core's checked-in **`preview.html`** renders the sidebar in isolation — **`just chrome-preview`** opens it (or `just preview` / `just shot` inside chrome-core), with `?density=compact` and `?header=1` (preview the nav-pill header slot + a live banner-height readout) URL params. See chrome-core's CLAUDE.md for the full loop.
- **Terminal-only vs browser-only affordances are DTO/callback differences, not ports.** A terminal has session state, so warden's unload *kills* the terminal (no cheap re-fetch, no curator-style reload-on-click). curator's browser nav (back/forward/home/reload) mounts into the component's optional `header` slot, which warden leaves null.

## Shared release tooling + Tauri runtime: `shell-core`

The third shared core (`https://github.com/Lockyc/shell-core`), alongside chrome-core and config-core,
consumed by git-rev pin. It owns the build/release tooling and the byte-identical sliver of Tauri setup
that is the same for warden, curator, and any future sibling app.

- **Release scripts are generated, not tracked.** `crates/warden-app/build.rs` calls
  `shell_core::materialize_scripts("../../scripts")`, writing `scripts/{release,gen-latest-json,install-app}.sh`
  **git-ignored** from the pinned rev. The generic scripts read the tracked `scripts/tooling.env`
  (`APP_NAME`/`TAURI_CRATE_DIR`/`UPDATER_REPO`); everything else derives. **Edit them in shell-core**, never
  here — the local copy is overwritten on the next build. So warden and curator run **one** shared release
  script (the `scripts/release.sh` mentions above and under *Releases* resolve to that generated file).
- **The build stamp comes from shell-core.** `build.rs` calls `shell_core::build_stamp()`, emitting
  `BUILD_GIT_SHA`/`BUILD_DATE`; the app-menu About item reads them via `env!` (warden previously had no
  build stamp — this closed the asymmetry with curator).
- **Plugin registration comes from shell-core.** `main.rs` registers window-state + updater + process via
  `shell_core::register_plugins(builder, window_state_filename(), &[DIAG_LABEL, LAUNCHER_LABEL])`. window-state
  stays a direct dep (manager.rs uses `WindowExt::restore_state`); `window_state_filename` (the `fnv1a_64`
  hash) is warden's own and passed in — only the registration is shared. The `runtime` feature pulls tauri;
  the `build.rs` build-dep uses `default-features = false` so it stays zero-tauri (resolver 2 keeps the two
  separate).
- **Deliberately NOT shared** (each diverges per app, don't consolidate): IPC fan-out, the config watcher,
  menu construction, and the chrome-caller command gate (curator-only — warden hosts no untrusted webviews,
  so it has no such gate). See shell-core's CLAUDE.md for the full dividing line.
- Dev loop: **`just shell-dev`** / **`just shell-pin`** (rev in `crates/warden-app/Cargo.toml`, scoped
  `#PATCH:shell#`), mirroring the chrome-/config- pairs.
- **Follow-up — a scriptable "open window by title" entry point belongs here (shared).** Nothing outside the
  app can open/raise a specific window today: it's GUI-only (Window menu, launcher, notification), and a
  second `open -a warden --args …` is silently dropped — there's no `tauri-plugin-single-instance`,
  `tauri-plugin-deep-link`, or CLI-arg handling. Build the entry point **in shell-core** so warden, curator,
  and future siblings inherit one implementation (same shape as `register_plugins`): single-instance argv
  (`--window <title>`) or a `<scheme>://window/<title>` deep link, forwarded to the already-running instance
  and mapped title → open-or-focus. Driver: a window configured `open_on_start = false` can't be opened
  by a login script, a shortcut, or any other automation today — only by hand from the launcher or the
  Window menu. This closes that gap.
