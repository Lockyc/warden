# warden — agent orientation

## What warden is

warden is a **config-driven terminal multiplexer** — "curator for terminals." A single TOML file is the source of truth: it defines **windows** and the **project tabs** inside them. The app materializes itself from that config and **hot-reloads on save**. Each window carries a colour + title banner for at-a-glance identity; each tab is a real terminal opened in a working directory running an optional command. warden is **generic and content-agnostic** — it knows nothing about any specific tool; the command a tab runs is arbitrary (a shell, a TUI, an agent launcher, whatever).

Target platform: **macOS**. Linux is a *possible future consideration, not a guarantee* — the `warden-config` crate is kept platform-neutral (pure logic, no macOS-only APIs) so that door stays open, but nothing commits to shipping Linux. Windows is unaddressed today, not ruled out: the terminal surface is a macOS-native `NSView` embed behind the `TerminalSurface` seam (see below), so a port would need a new per-OS shim behind that same seam — revisit if a Windows backend is ever wanted.

## Current state — read this before assuming anything exists

Two layers are built:

- **Config-core** — the `warden-config` crate (pure logic, no GUI): parses/validates/resolves the TOML, diffs two configs for hot-reload, loads from disk, watches the file, ships a `warden validate` + `warden fmt` CLI.
- **GUI** — the `warden-app` crate: a config-driven, multi-window **macOS-only** Tauri app. What's built (README = the user-facing tour; [`docs/config.md`](docs/config.md) = the schema; [`docs/probing.md`](docs/probing.md) = presence probing; *Conventions & footguns* = the traps):
  - **A native window per `[[window]]`**, materialized at launch (gated by `open_on_start`), each with a colour + title banner and curator-style transparent chrome (Overlay titlebar, opaque draggable sidebar). Window size/position persist per Tauri label (in AppKit points); sidebar width persists in `localStorage`.
  - **Tabs = embedded libghostty surfaces** behind the `TerminalSurface` seam, lazy-spawned on first focus (except `load_on_open`). Sectioned by `[[window.group]]` and auto-discovered from `[[window.root]]` project trees (`scanner.rs` → `synthesize_tabs`, rendered as a collapsible tree; rescan on open / hot-reload / manual refresh — no fs watcher).
  - **Tab-row dots:** live/cold (spawned?) doubling as an **unload** ✕ (kills surface+PTY → cold, respawns on next focus; unloading the visible tab leans **up** to a live neighbour, else a blank placeholder); amber **attention** badge on bell / OSC 9 / OSC 777 (decoded via `action_cb` → `notify.rs`; background tab badges, and a desktop-notify also raises a macOS banner via native `UNUserNotificationCenter` — **clicking the banner raises that window + selects the tab**); cyan **session-presence** dot (per-tab `probe`, off-main-thread scheduler; **three** states — cyan
  = live session on exit 0, a **ghost** = crashed-but-restorable on exit 3, hollow = nothing. The
  ghost is pure decoration on the existing start affordance: clicking it types the same `cmd`, and
  the canonical `amux --probe` exits 3 exactly when a plain `amux` launch would offer its restore
  picker) doubling as a **kill** (two-step confirm — `⏻` kills the session only and leaves the terminal live; `☠` kills the session **and** unloads the terminal in one action, via chrome-core's optional `onKillClose`) / **start** (types `cmd` into the live shell) toggle.
  - **Persistence & empty states:** warden is a **persistent app** — closing the last real window doesn't quit (⌘Q does). A single `sync_empty_surface` authority picks, whenever zero real windows are open, what the **shared home surface** (`shell-core`'s `home::{home_state, show_home, close_home}`, replacing warden's own former `launcher.html` *and* its former `diagnostic.html`) shows: `NoConfig` (no file on disk — "Create a starter config"), `Broken` (a file that exists but didn't load — shows the error, "Edit Config"), or `Windows` (a valid config; lists every configured window, possibly empty — a config that parses but declares zero `[[window]]` entries is an empty list, not an error; click a row to raise/reopen). `home_state` itself picks the state from `has_windows`/`config_exists`/`load_error`/the window list; a mid-edit *parse* error while real windows are still open instead keeps them up behind an error banner (the home surface stays closed, since `has_windows` wins). `WindowManager::load_error` is the persisted status `home_state`'s `Broken`/`NoConfig` choice reads — set on every failed load, cleared on every successful one — since `sync_empty_surface` runs from places with no load context of their own (e.g. a window's `Destroyed` handler), so it can't take the error as a parameter the way curator's `reconcile_home` does. The home surface is a special non-counting window (own label, invisible to `is_empty()`), and its `Destroyed` handler quits the app when it was the last surface, in whichever state it happened to be showing.
  - **Terminal affordances from libghostty's action stream** (`surface/ghostty.rs::action_cb`): **clickable links** — an `NSTrackingArea` forwards `mouseMoved`/`mouseExited` so libghostty can resolve the cell under the cursor (its link detection runs on that; without motion, URLs were wholly inert), then `MOUSE_SHAPE` drives the AppKit cursor via cursor rects (I-beam over cells, hand over a link) and `OPEN_URL` hands the clicked link to `NSWorkspace`. **Dead tabs** — `SHOW_CHILD_EXITED` unloads the tab back to **cold** (dot dark, focus the row to respawn) instead of leaving libghostty's "Process exited" overlay live forever; it reuses `Registry::unload`, so a process dying and a manual ✕/⌘W land the chrome in the same state (shared `applyUnloaded` in `index.html`, driven by `warden:tab-exited`).
  - **Hot-reload** is live (watcher + `reconcile` → per-window open/close/refresh; a window *title* change is destructive = close+open).
  - **App menu** (rebuilt on launch / window-set change / `tab_digit_keys` flip, with the `ManagerState` lock released): **App, Config, and Window are the shared spine** (`shell_core::menu::build_spine`) — Config (edit / reveal) and Window (list + reopen, checked when open) are identical to curator's and lector's. **The Tab submenu's navigation items are shell-core's too now**: ⌘⇧[ / ⌘⇧] cycle *loaded* tabs, ⌘1–9 jump, or ⌘1/⌘2 cycle under `tab_digit_keys = "cycle"` — built by `shell_core::menu::build_tab_nav(app, mode.is_cycle())` and routed by `shell_core::menu::tab_nav_action(id)`, so the mode's effect (which ids exist, which chord each claims) is defined once for all three apps, not per app. What stays warden's own is the **submenu composition** (`build_app_menu` interleaves the nav items with the spine's `Close Tab`/`Pop Out Tab` and the jump items) and the **terminal semantics** of those spine items: ⌘W unloads the active tab, NOT the window (⌘⇧W closes the window — the spine's own accelerator, unchanged, warden already had this right); **⌘⇧O pops the active tab out** (see the Pop-out bullet next). **Reopen Last Closed (⌘⇧T)** is warden-only and is spliced into the spine's already-built Window submenu rather than added to the spine itself (curator and lector have no equivalent — YAGNI to add it speculatively).
  - **Pop-out (session-preserving):** a ⤢ control on each tab row (chrome-core's `onPopOut`) and **Tab ▸ Pop Out Tab (⌘⇧O)** pop the **active** tab into its own temporary **banner-only window** — shell-core's shared detach shell (title + accent, no sidebar). **Session-preserving is the defining property**: `GhosttySurface::reparent` moves the live surface's NSView onto the new window's content view (drops + re-registers its three window-scoped observers against the new window, swaps the `window` field, re-seeds display-id + focus from the new window's real key state, reapplies geometry) and calls **none** of `teardown`/`ghostty_surface_free`/`close` — the PTY, scrollback, and running process survive both the pop-out and the return trip untouched. `Registry::detach` extracts the `Spawned` surface, leaving a **`TabSlot::Detached` placeholder** in the origin (never freed); **closing the detached window returns the tab to its origin** (reopening the origin first if the user closed it while the tab was out), via `Registry::attach` (`Cold`/`Detached` → `Spawned`). The lock-discipline, reconcile-safety, and chrome-forwarding invariants that keep this from deadlocking, duplicating a tab, or dropping a live PTY are in *Conventions & footguns* below.

Deferred (see [`docs/FOLLOWUPS.md`](docs/FOLLOWUPS.md)): ad-hoc `⌘T`/`⌘N` tabs; `TerminalSurface` seam hardening; FFI repr hardening (the C-populated `#[repr(C)]` enum *fields* — the action-tag discriminants are now generated, see the footgun); IPC hardening (a restrictive CSP ships; dropping `'unsafe-inline'` + reviewing `withGlobalTauri` remain); watcher debounce; argv passthrough.

## Intended architecture (where it's going)

- **Tauri** (Rust core + web chrome), one app, macOS-first. Tauri's cross-platform nature keeps a future Linux port viable, but macOS is the only committed target.
- **Windows = native macOS windows** — each `[[window]]` in config is one window (macOS `cmd+\`` cycles them), with its own colour + title banner. **Tabs = projects** within a window, cycled by a secondary keybinding. A single app/dock-icon by design — per-window identity is carried in-app via the banner, not via separate app bundles.
- **Terminal surface = embedded libghostty** behind a `TerminalSurface` seam — a small per-OS native shim hosts the surface (NSView on macOS; a GTK widget would host it on Linux if that port ever happens). A non-libghostty fallback impl (e.g. SwiftTerm-class) can sit behind the same seam. libghostty's embedding C API is officially unstable — **pin it** to a known commit.
- The `warden-config` crate is the foundation the app consumes (window/tab set, hot-reload reconcile, watcher).
- **Splits within a tab are warden's to grow, not a multiplexer's to provide** — the direction, the evidence, and what it unlocks (an out-of-band surface for agent-produced images — warden's embedded surface already renders the kitty graphics protocol, no pin move or wiring needed) are in [`docs/native-splits-direction.md`](docs/native-splits-direction.md). Read it before adding a terminal capability a multiplexer would otherwise supply, or before assuming a split has to come from tmux.

## Workspace layout

Cargo workspace. `crates/warden-config` — the config crate (a library plus the `warden` CLI binary). Data flows one direction through small, independently-tested modules:

```
raw.rs       serde structs mirroring the TOML schema + parse()
  ↓
resolve.rs   validate + fill defaults + expand ~ → (Config, Vec<Warning>); ResolveError
  ↓
model.rs     clean resolved types: Config / Window / Tab / Warning
reconcile.rs reconcile(old, new) → Reconciliation (open/close windows, per-window colour/tab-add-remove/tab-reorder/set_meta relabel/respawn_tabs) for hot-reload
load.rs      load(path) = read+parse+resolve; config_path() (WARDEN_CONFIG override else ~/.config/warden/config.toml); LoadError
watch.rs     Watcher — notify-based parent-dir file watcher; fires load() on change
(fmt + colour live in the shared config-core crate — re-exported at warden-config's root as format_str/format_file + Colour/ColourError; the `warden fmt` subcommand itself delegates to config-core's shared `fmt_cli` — `bin/warden.rs` only resolves the default path — so `warden fmt` + `curator fmt` are one implementation, while `warden validate` stays here (warden's own schema); see Config formatting footgun)
bin/warden.rs  `warden validate [path]` + `warden fmt [--check] [path]` CLI
```

`crates/warden-app` — the macOS Tauri app that consumes the config crate. Key modules: `plan.rs` (config → `WindowSpec`/`TabPlan`, `reconcile` → `WindowOp`; `derive_tree_meta` computes each tab's tree/tree_path from the window's roots, via config-core's re-exported `tree_path`), `manager.rs` (`WindowManager`: materialize windows, apply reconciliations, the `sync_empty_surface` home-surface authority; `effective_config` expands `[[window.root]]`s into synthesized tabs), `scanner.rs` (`synthesize_tabs`: maps config-core's leaf-free `discover_projects` — the actual filesystem walk lives there, shared with lector — onto warden's own `Tab`; no AppKit/Tauri, unit-tests against temp dirs), `registry.rs` (per-window tab registry over surfaces), `surface/` + `ffi/` (the libghostty embed behind the `TerminalSurface` seam — macOS/objc2), `geometry.rs` (web-rect ↔ NSView-rect). `ui/index.html` is the chrome. The no-windows surface is shell-core's shared `home.html` (`NoConfig`/`Broken`/`Windows`), embedded in the pinned shell-core crate rather than tracked here — it replaces both the former `ui/launcher.html` and `ui/diagnostic.html`, neither of which exists anymore.

## Config schema (`~/.config/warden/config.toml`; override with `WARDEN_CONFIG`)

**Full reference — every key, the cascade rules, and validation — is in [`docs/config.md`](docs/config.md); read it before touching config parsing/resolution.** The README's *Config ▸ Every option* tables are the user-facing copy of that same key list — the public face indexes **every** option, so **a new config key lands in `docs/config.md` *and* the README tables in the same change as the parser**; the README's example block is a deliberate subset and is not the surface. In brief: the file has global defaults, then `[[window]]` blocks (native macOS windows) holding `[[window.tab]]` project terminals. Tabs can be sectioned by `[[window.group]]` (presentation only) or auto-discovered from a `[[window.root]]` scanned projects dir. `shell`/`cmd`/`probe`/`kill` **cascade** (global → window → tab, or root → window → global for discovered projects; nearest set level wins, `""` opts a level out). Load-bearing invariants that bite if forgotten:

- **`cmd` is typed *into* the shell, not exec'd** — it's libghostty `initial_input`, so a shell *function* like `amux` resolves and the shell survives the command exiting. Don't pass it as libghostty's `command`/exec target.
- **Tab identity is `id`-else-normalized-`dir`, never the title** (`Tab::key`); `title` is a pure, repeatable display label. Curated + discovered tabs share this dir-keyed scheme, so a curated tab **shadows** a same-dir discovered project.
- **Groups add no cascade level and roots add one** (root→window→global); both flatten to the single ordered `Tab` list with a `group` tag — the flat list is the only downstream shape.
- **Resolution collapses the cascade** to flat `Tab.shell`/`Tab.startup`/`Tab.probe`/`Tab.kill`; the app never sees the levels. `density`/`tab_digit_keys` are global, no cascade, unknown value → `ResolveError`.
- **Validation** errors on duplicate window title / tab identity / section name, empty required fields, bad colour, non-positive size, root `depth < 1`; a missing `dir` is a *warning* (created anyway). Invalid config is reported, never panics.

The probe **scheduler** internals (bursts, `PresenceCache`, the single-driver rule) live in [`docs/probing.md`](docs/probing.md); the config-adjacent traps (format-on-save, the probe/kill exec environment, tab-identity reconcile shapes) are in *Conventions & footguns* below.

## Build / test / run

- `cargo build` / `cargo test` (workspace). `warden-app` is macOS-only (libghostty embed); it fails to compile elsewhere by design.
- **Toolchain is pinned** in `rust-toolchain.toml` (with `rustfmt`+`clippy`) so formatting and lints are identical for everyone — an unpinned `stable` drifts and re-wraps committed code, which has bitten `just fmt`/`just check` here. rustup auto-installs the pinned version; the file is the source of truth for the channel, so don't restate it here. **config-core carries the canonical pin — bump it there first, then match it in `rust-toolchain.toml` here and in curator's and lector's** (shell-core matches too, so its own gate is meaningful standalone; chrome-core deliberately carries *no* pin — its gate floats and is advisory, so there's nothing to bump there). The cores are all *git dependencies* (chrome-core and shell-core also *build*-dependencies), so their own pins don't apply when warden builds them — warden's toolchain compiles the whole graph, and a core's pin governs only developing that core standalone. Bump the apps together, naturally when bumping a shared crate's pinned rev.
- `cargo run -p warden-config --bin warden -- validate [path]` — validates a config and prints the resolved window/tab tree + warnings (exit 0 ok / 1 load error / 2 usage).
- `cargo run -p warden-config --bin warden -- fmt [--check] [path]` — formats a config in the shared house style (config-core's taplo-backed formatter — no external taplo binary needed). `--check` is non-mutating and exits 1 if the file would change (for a pre-merge gate).
- `cargo run -p warden-app` — launch the GUI (reads `WARDEN_CONFIG` or `~/.config/warden/config.toml`).
- **`justfile`** wraps the common flows: `just run` (launches the app against `examples/config.toml` via `WARDEN_CONFIG`, so iterating never touches your real config), `just validate [path]`, `just test`, `just check`, `just fmt`, `just clippy`; bare `just` lists them.
- **`just hooks` — once per clone, or neither git hook exists.** `core.hooksPath` is per-clone *local* git config, so the repo cannot carry it: a fresh clone has **no** docgraph pre-push gate and **no** active-`[patch]` pre-commit guard until `just hooks` runs. Both are described elsewhere in this file as live safety nets — they are only live once switched on. `.github/workflows/ci.yml` runs the same fmt/clippy/test gate on push + PR to `main`/`dev` (macOS runner — `warden-app` compiles nowhere else), so CI is the backstop when a clone forgets.
- **Vendored libghostty** (`crates/warden-app/vendor/GhosttyKit.xcframework`, the terminal-surface embed) is Ghostty compiled from a **pinned, unmodified upstream commit** by [`lockyc/libghostty-build`](https://github.com/lockyc/libghostty-build) (its CI builds Ghostty's own `-Demit-xcframework` target on `macos-15` with Zig 0.15.2 — the runner-OS choice is what sidesteps the Zig-0.15.2-vs-macOS-26-SDK link failure), published as a release asset and pulled in via **`just revendor-ghostty`** (downloads the latest release, verifies its sha256, swaps `vendor/`). The universal `libghostty.a` is committed (~48MB, debug-stripped). The same release also carries libghostty's **runtime resources** (`vendor/resources/`), which warden must ship — see the terminfo footgun below. To move Ghostty versions: bump `GHOSTTY_REF` in libghostty-build → its CI republishes → `just revendor-ghostty` → update `vendor/PROVENANCE.md`. **Watch the FFI on a version jump:** libghostty's embedding C API is officially unstable, so after a bump diff `vendor/…/Headers/ghostty.h` against `ffi/mod.rs` — struct sizes are guarded by `const _` `size_of!` asserts that fail the build on drift (that's how the v1.3.1→main jump surfaced `ghostty_surface_config_s` shrinking 120→88 bytes when the host-managed IO backend was removed), and the **action-tag discriminants are generated from the vendored header by `build.rs`** (`ACTION_TAGS` names them; the header supplies every value), so a reordered enum can no longer rot a hand-copied number — a *renamed* tag fails the build. Still eyeball any other enum transcribed positionally (`cursor_for_shape`).
- **Packaging:** `just build` produces the release `warden.app` (needs the Tauri CLI — `cargo install tauri-cli --version ^2`); `just deploy` (now via `install.sh`) installs it to `/Applications` and relaunches. Release builds are **signed with Developer ID and notarized + stapled automatically** when the Apple signing/notary env vars are present in the build environment — `APPLE_SIGNING_IDENTITY` pointing at a Developer ID Application cert, plus `APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID` (or `APPLE_API_KEY`/`APPLE_API_ISSUER`/`APPLE_API_KEY_PATH`); Tauri runs the signing and `notarytool` submission (with hardened runtime) during `cargo tauri build`. With those vars unset (e.g. a contributor building from source), the build falls back to an ad-hoc/unsigned bundle, and `scripts/install-app.sh` strips the Gatekeeper quarantine xattr so a local copy runs either way. This is env-driven, not pinned in `tauri.conf.json`, so a build environment without the vars silently ships unsigned — set them to ship a distributable release. **macOS 26 footgun (why `just deploy` re-signs locally):** macOS 26 runs a per-exec provenance/quarantine check in syspolicyd (`qtn_proc`) that *fails* for an ad-hoc, team-less bundle **and every process it spawns** — for a terminal like warden that hosts your shells, that failure fires on every command run inside it, storming syspolicyd + kernel_task (measured: ~4100 `qtn_proc` failures/10s → syspolicyd at ~37% CPU; the whole subtree, not just warden). A real **Team ID** takes the check's cached fast-path instead, so the `deploy` recipe auto-detects a *Developer ID Application* identity via `security find-identity` and re-signs the installed bundle with it (`--options runtime`, no notarization, no env vars — distinct from the release path's env-driven notarized signing). Verified fix: signing dropped `qtn_proc` failures 4100 → 0. No Developer ID cert in the keychain → deploy warns and leaves it ad-hoc (expect the storm on 26). The generic sibling accommodation (`install-app.sh`'s quarantine-xattr strip) lives in shell-core; the Dev-ID re-sign is warden-local in the `deploy` recipe because a blanket hardened-runtime re-sign isn't safe for every consuming app. The bundle icon is `crates/warden-app/icons/icon.icns`, produced from the SVG masters by `assets/build-icons.sh`.
- **Releases:** the version is **single-sourced in `crates/warden-app/Cargo.toml`** — `tauri.conf.json` deliberately has **no `version` key** so the bundle inherits Cargo.toml's (don't re-add it; two version fields silently drift and the `.app` ships mislabelled). `warden-config` keeps its own independent version; the release tag tracks `warden-app`. Cutting a release (`main` tracks the latest release and is a clean ancestor of `dev`): on `dev`, bump `warden-app`'s version + refresh `Cargo.lock` → `chore(release): warden <v>` commit → `git tag v<v>` → fast-forward `main` to it → push `dev`, `main`, the tag → `gh release create v<v>` with notes summarising what shipped since the previous tag → **`just release`** (= `scripts/release.sh`) to build the notarized `warden.app`, `ditto`-zip it to `warden-<v>-macos.zip`, attach it, **and attach the updater artifacts** (`warden.app.tar.gz` + `.sig` + `latest.json`, via `scripts/gen-latest-json.sh`) so existing installs auto-update. `scripts/release.sh` reads the version from Cargo.toml and **refuses to run unsigned** (no `APPLE_SIGNING_IDENTITY` → exit) *and* without the updater key (no `TAURI_SIGNING_PRIVATE_KEY` → exit), so neither an un-notarized zip nor an unsignable/un-updatable release can masquerade as official. See *In-app updates* below for the updater key + endpoint.

- **In-app updates:** warden updates itself via `tauri-plugin-updater` (+ `tauri-plugin-process`), mirroring curator. **The self-updater is an app-agnostic capability owned by chrome-core** (see chrome-core's CLAUDE.md dividing-line decision — an updater is an *app* feature, not a terminal/browser one): the check + install/relaunch + the re-check cadence live there once so every app inherits one implementation. warden's controller (`ui/index.html`) only passes its `auto_update` gate to chrome-core (`autoUpdate` in the mount config) and forwards the menu event to `sb.checkForUpdateNow()`; it keeps warden's updater *identity* (endpoint, pubkey, plugin registration) below. So chrome-core checks on launch **and re-checks every chrome-core `UPDATE_CHECK_INTERVAL_MS` (6h)** (warden is long-running, so a window open for days still surfaces a release) when `auto_update` is on, plus on **warden ▸ Check for Updates…** (always, via `warden:check-update` → `checkForUpdateNow()`); a hit shows chrome-core's update bar (with a × that dismisses for the session) and, on confirm, downloads + installs + relaunches — **confirm-to-install**. Endpoint (zero-server): `plugins.updater.endpoints` → `https://github.com/lockyc/warden/releases/latest/download/latest.json`. The updater verifies its **own** minisign signature (separate from the Apple cert) over `warden.app.tar.gz`; the private key lives at `~/.tauri/warden-updater.key` (never committed), its public key in `tauri.conf.json` (`plugins.updater.pubkey`). Cutting a release supplies the key to `scripts/release.sh` via `TAURI_SIGNING_PRIVATE_KEY` (contents/path of that file) + `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, both required in the build env alongside the Apple notary creds (see *Packaging* above; see `docs/FOLLOWUPS.md` for a deferred idea on sourcing the passphrase from the macOS Keychain). **`createUpdaterArtifacts` is enabled release-only via `scripts/release.sh`'s `--config` override, NOT in the committed `tauri.conf.json`** (footgun: baking it in makes every `cargo tauri build` demand the signing key, breaking keyless `install.sh` / `just build` / `just deploy`) — so only the release build emits the signed tarball + `.sig`. The chrome is granted `updater:default` + `process:allow-restart` in `capabilities/default.json`. The release artifact is a **universal binary**, so `latest.json` carries both `darwin-aarch64` and `darwin-x86_64` pointing at the one tarball — shell-core's `gen-latest-json.sh` owns that, and its CLAUDE.md carries the keep-both-keys footgun. The **first** updater-capable release must be installed manually once (the bootstrap); every release after updates in-app. Unlike `density`/`sidebar_drag`, **`auto_update` is currently NOT wired into `main.rs`'s reload hook** (the global-config-hot-reload footgun below) — it's passed to chrome-core as `autoUpdate` once at init, and chrome-core arms both the launch check *and* the 6h re-check from it at that moment, so a hot-reload doesn't retroactively arm/disarm them on an already-open window: toggling `auto_update` currently takes effect next launch (restart-only). This is a **wiring choice, not a limitation** — making it live means re-arming chrome-core's launch/periodic checks from the reload hook the way `density`/`probe_interval` already re-run (roadmap: see `docs/FOLLOWUPS.md`), and it's simply not been worth it for a rarely-flipped update toggle. So it's out of the reload hook for now by choice — and it's not the "global-only won't hot-reload" bug.
- **Install from source:** `install.sh` (repo root) is the self-sufficient installer — `bash install.sh` from a checkout builds the current tree; `curl -fsSL https://raw.githubusercontent.com/lockyc/warden/main/install.sh | bash` clones/updates `~/.warden` and builds from it. Both backstop the Tauri CLI (`cargo install tauri-cli`), build via `cargo tauri build`, install to `/Applications/warden.app` (reusing `scripts/install-app.sh`), and seed `~/.config/warden/config.toml` if absent. `just deploy` delegates to `install.sh` (IN_REPO mode) then relaunches. The guided path is the **`/warden:install`** Claude command (`.claude/commands/warden/install.md`), which adds prerequisite checks and a config-edit/launch flow.

## Conventions & footguns (things that have bitten us / will bite again)

**The normal case is boring.** A TOML edit becomes windows + tabs; saving hot-reloads them. The subsystem itself is a straight config → materialize → reconcile pipeline — almost everything below is a *native-embedding* or *GUI-launch* edge: real traps, but rare ones, not the shape of the system. Each pointer names the rule in one clause and the code site whose comment carries the full why (verified to hold it) — read that comment before touching the site.

**Three premises the entries below lean on** (stated once, referenced by name):

- **Minimal GUI PATH.** A `.app` opened from Dock/Finder/Spotlight inherits only the launchd PATH (`/usr/bin:/bin:/usr/sbin:/sbin`), so a bare-name shell/probe/kill command is `exec: … not found` unless PATH is restored (`restore_login_path`) or the command is absolute.
- **Surfaces spawn focused.** libghostty inits every surface `focus = 1`, which starts its **60fps render display link**; only *clearing* focus stops it (drops the surface to change-driven rendering). A surface left wrongly focused burns 60fps — and, while a background TUI redraws, samples the text cursor mid-relay → the cursor flashing around an unfocused window.
- **A title change is destructive.** Changing a window's `title` is a close(old)+open(new): it kills and recreates that window's terminals (including `load_on_open` ones) and its persisted per-label bounds. Tab identity is `id`-else-normalized-`dir`, **never** the title (`Tab::key`; full scheme in [`docs/config.md`](docs/config.md)).

### Cross-cutting rules (no single call site owns them)

- **No transitional fallbacks.** Young codebase — finish every migration in-branch; no dual-shape accessors or `TODO: remove after rollout` scaffolding. (Global CLAUDE.md's *no legacy hangers-on* is the why.)
- **Keep tool-specific concepts out of the `warden-config` crate.** The crate stays generic (neutral test command strings); the **README/public face** deliberately names [agentmux](https://github.com/lockyc/agentmux) (`amux`) as the canonical companion (the `warden → agentmux → tmux` stack). Don't leak agentmux into the crate, and don't strip the link from the README.
- **Raw-string TOML fixtures with a colour hex** self-terminate at `"#` inside `r#"…"#` — use `r##"…"##` for any fixture containing `colour = "#…"`. (Hit repeatedly across modules.)
- **NEVER move the user's real `~/.config/warden/config.toml` aside to test `NoConfig`/`Broken`** — point `WARDEN_CONFIG` at a nonexistent path: `WARDEN_CONFIG="$(mktemp -d)/nonexistent.toml"` reproduces `NoConfig` exactly (`home_state` keys on `path.exists()`) with nothing to restore. Moving the real file has already destroyed a config once — the destructive `mv` and its restore sat in separate steps and the restore never ran.
- **Testing the deployed `/Applications/warden.app` needs no destruction either:** `open --env "WARDEN_CONFIG=<path>" -a /Applications/warden.app` propagates the override — but it is **silently ignored if warden is already running**, and warden is persistent (closing every window does *not* quit it, ⌘Q does). So force-quit first (`osascript -e 'quit app "warden"'`), then `open --env`.
- **"No notifications at all" (not even the amber badge) is an upstream *transport* failure, not a warden bug.** warden badges/banners only when the OSC 9/777 escape reaches its surface. The canonical producer (agentmux `--notify`) must wrap the OSC **once per nested tmux layer** — under `amux --frame` (two tmux deep) a single wrap is unwrapped by the inner tmux and dropped before warden sees it (fixed in agentmux ≥ 0.14.0). Diagnose at the agent→frame boundary: `tmux -L agentmux-frame pipe-pane -t <agent-pane> 'cat >> /tmp/cap'` — a bare `]777` crossing = dying at the frame; a `Ptmux;` envelope = it'll reach warden. (Badge-but-no-banner is instead the auth/OS case — next rule.)
- **An OSC 8 hyperlink that renders as inert styled text under tmux is the tmux hop, not warden's link handling.** warden's two link paths both work (both still gated on mouse reporting — next entry): libghostty regex-matches URL *text* in the cells, and honours an OSC 8 hyperlink over arbitrary label text (`MOUSE_SHAPE` → hand cursor, click → `OPEN_URL`). But tmux re-emits a hyperlink only when its client has the `hyperlinks` **terminal feature**, and derives that from the terminfo `Hls` capability — which the bundled `xterm-ghostty` does **not** ship (`infocmp -x xterm-ghostty` has no `Hls`). So tmux forwards the label and strips the URL, leaving nothing on screen for the regex path either: the link is silently dead, and no amount of warden-side work fixes it. Fix is one line per socket in the *tmux* config — `set -as terminal-features 'xterm*:hyperlinks'` (agentmux sets it in `tmux/{agentmux,frame,term}.conf` and re-asserts it on the long-lived frame socket; a plain-tmux user needs it in their own `~/.tmux.conf`). Note this is *sharper* than the `Sync` case, where the cap ships and tmux ignores it. Features are computed at **client attach**, so it lands on the next reattach, never on the live client — and `#{client_termfeatures}` is the one-command diagnostic.
- **Under tmux `mouse on`, a link needs SHIFT — to hover *and* to click.** This one is libghostty behaving as designed, so it is the *second* thing to check, never the first: a shift-click that still does nothing means something upstream of it is broken (it was the action-tag drift below). tmux with `mouse on` turns mouse reporting on for warden's surface, and Ghostty refreshes link state only when `mouse_event == .none` **or** shift is held and `mouse-shift-capture` is off (`Surface.zig::cursorPosCallback`, at the rev in `vendor/PROVENANCE.md`). So `mouse.over_link` never goes true — and the release-time link click is gated on exactly that flag (`mouseButtonCallback` → `processLinks`) — hence no underline, no hand cursor, no `OPEN_URL`, for the regex path *and* the OSC 8 path alike. Shift is the standard mouse-reporting bypass (Ghostty.app and iTerm behave identically), and warden inherits it free: `mods_from_event` already reports SHIFT, and `ghostty_config_load_default_files` leaves `mouse-shift-capture` at its default `false`. Diagnostic: `tmux -L <socket> show -g mouse`. This sits *downstream* of the entry above — the terminal-feature fix makes the link exist at all; shift is what lets you touch it. Verify with shift *before* concluding warden's link plumbing works.
- **A libghostty action that silently stops firing after a revendor is tag drift, not the feature.** `ghostty_action_tag_e` is a valueless C enum, so every tag is its 0-based position — and upstream inserts members mid-list. A revendor that added `CHECK_FOR_UPDATES` shifted `OPEN_URL` 55→54 and `SHOW_CHILD_EXITED` 56→55 against warden's hand-copied numbers, and **nothing failed**: the `const _` `size_of!` asserts guard struct *layout*, not discriminants. Three symptoms from that one off-by-one — clicking a link did nothing (real `OPEN_URL` matched no arm), a dying child decoded as `OPEN_URL` and read a garbage `(ptr, len)` (a wild-pointer slice, not a crash we ever caught), and a progress report decoded as `SHOW_CHILD_EXITED` and unloaded a live tab. **Fixed structurally: `build.rs::generate_action_tags` derives the values from `vendor/ghostty.h` into `$OUT_DIR/action_tags.rs`** (`ffi/mod.rs` `include!`s it), asserting the enum still carries no explicit values. Never re-inline a discriminant, and add a new tag by name to `ACTION_TAGS`.
- **A missing banner while the badge *does* show, on macOS 26, is the OS — not `notify.rs`.** Every readable signal says the banner should render (OSC decodes, tab seen not-visible, `willPresentNotification` returns `.banner`, `getNotificationSettings` Authorized) yet macOS 26 drops it (a known presentation regression, with a foreground-only variant). Don't rewrite `notify.rs` chasing it — the warden side is verified correct; the fix is the OS. Discriminator, trace capture, and OS fixes: `docs/notifications.md`.
- **A mousedown drags only if the element *under the cursor* carries `data-tauri-drag-region`** — a child never inherits it from an ancestor. chrome-core owns the traffic-light zone (`#cc-titlebar`); warden's `#sidebar` carries the attribute for the body.

### Call-site pointers (rule here, full why in the named code comment)

- **`open` forwards the caller's environment — deploy launches via shell-core's `scripts/launch-app.sh`, never a bare `open`** or warden inherits the deploying terminal's context and hands it to every tab's shell (`TERM_PROGRAM`, `TERMINFO`, `GHOSTTY_*`, `ATUIN_*`/`STARSHIP_*`, `CLAUDE_*`, and `SHELL`, which `login_shell` reads — so tabs open the deploying shell, not your login shell). Process parentage is already clean (launchd); only the env leaks, and `main.rs`'s targeted scrubs can't chase all of it. The script (shared with curator + lector, materialized git-ignored) carries the full why. Symptom: "warden misbehaves from `just deploy` but is fine from Spotlight."
- **Icon safe area:** the app tile must sit in an 824×824 box on the 1024 canvas or it renders ~25% oversized in the Dock / cmd-Tab — enforced in `assets/build-icons.sh` (design the SVG edge-to-edge; don't drop the wrapper). Recurs on every app; the script-level enforcement is the durable fix.
- **Seed a spawned surface's focus from real key state** (*surfaces spawn focused*): a background window's surface left focused burns 60fps and flashes the cursor — `surface/ghostty.rs::new`, right after `set_surface`. Don't drop it expecting the key observers to cover it (a never-key window emits neither).
- **`hide()` must clear the surface's focus:** hiding a view doesn't stop its render display link, so an off-screen tab keeps rendering at 60fps — `GhosttySurface::hide` (`surface/ghostty.rs`). Measured 2.6× CPU on 5 streaming tabs.
- **Ship libghostty's terminfo or every tab is a plain `xterm-256color`** (no `Sync` cap → tmux doesn't bracket redraws in DEC 2026 → full-redraw *tearing*): bundled via `tauri.conf.json` `bundle.resources` + `main.rs::configure_ghostty_resources` (clears an inherited `GHOSTTY_RESOURCES_DIR`; debug points at `vendor/resources/`). One-command check: `echo $TERM` in a tab.
- **Never free a surface from inside `action_cb`** — libghostty is still standing on it (a silent use-after-free that *tests* fine); the `SHOW_CHILD_EXITED` path defers via `dispatch_async_f` — `surface/ghostty.rs`. Any future surface-destroying or lock-taking action must take the same deferred path.
- **The watcher matches the config by file name, not full path** (survives FSEvents `/private/var` vs `/var` symlinks and atomic-save inode swaps) and fires on *any* event — `warden-config/src/watch.rs`. Don't restore full-path equality or add an `event.kind` filter.
- **`rescan_root` diffs a fresh scan against `last_good` (what's on screen), not two scans against each other** — `main.rs::rescan_root`. Don't "simplify" to comparing two scans directly (it would miss drift the screen hadn't caught up to).
- **Window bounds restore is per-label, via shell-core's geometry plugin's own `on_window_ready` hook** (it fires for runtime-built windows too — no manual trigger needed, and none should be added, see the FOOTGUN in `manager.rs::build_window`); the label derives deterministically from the title, so a *title change* restores fresh default bounds (consistent with *title change is destructive*).
- **A surface that fails to spawn degrades to a cold tab — never `.expect()`/`unwrap()` it** (one bad tab used to panic the whole app at launch): errors ride the init snapshot (launch-time) or `warden:error` (click-time) — `registry.rs` (`add`/`ensure_spawned`/`activate`).
- **A new *global* config setting won't hot-reload if only threaded through the per-window DTO** ("density-only edit does nothing"): a global-only edit is an empty reconcile, so add its own old-vs-new compare in the reload hook — launch works via `InitDto`, which is the trap. `main.rs` reload hook.
- **`emit_to` leaks to sibling webviews** — every per-window event must stamp a `label` and the chrome filters on it (`forMe()`): `main.rs` (`on_menu_event`), `manager.rs` (`warden:refresh`), `notify.rs`, `probe.rs`. Don't add a per-window emit relying on `emit_to`'s targeting alone.
- **Never add an optimistic dot-clear on kill** (reintroduces the off→on→off flicker): the presence dot tracks `warden:session-state` alone and converges monotonically; kill runs to completion before a directional `bump_tab_await(false)` — `main.rs::kill_session`.
- **Default shell = `$SHELL -l`, absolute** — sidesteps the *minimal GUI PATH* trap by construction; a config `shell` override is arbitrary and may be bare (covered by `restore_login_path`) — `main.rs::login_shell`.
- **`restore_login_path` imports the login-shell PATH at startup** so bare config shells/probes/kills resolve from a Finder launch (*minimal GUI PATH*); best-effort, 3s deadline, never worse than no-op — `main.rs::restore_login_path`. Don't remove it expecting the absolute-`$SHELL` default to cover config overrides.
- **Probes inherit warden-app's process env:** PATH is handled by `restore_login_path`, but arbitrary shell *exports* aren't, so the canonical probe names `amux` by absolute path (`"$HOME/.agentmux/bin/amux" --probe`) — `probe.rs`.
- **The probe child's `$PWD` is the configured `dir`, not the physical `getcwd()`** — `run_probe` sets it explicitly (`current_dir` alone doesn't), so warden's probe and the tab's own shell agree on the tab's directory when the config path reaches it via a symlink or different case. Don't drop it: a `$PWD`-keyed probe (amux shards its sockets on `cksum "$PWD"`) otherwise misses its own session — `probe.rs::run_probe`, which `kill_session` also runs through.
- **The probe *scheduler* is the single driver** — off-main-thread, background-QoS sweep workers, bounded concurrency, per-tab changed-only `label`-stamped emits, and a `PresenceCache` first-paint replay written per-tab-before-emit. Don't serialize the sweep, drop the QoS demotion, batch the cache write to end-of-pass, or add a one-shot reprobe (triggers `bump`/`bump_tab_await`). Full mechanism: `probe.rs` comments + [`docs/probing.md`](docs/probing.md).
- **macOS banners go through native `UNUserNotificationCenter`, not `tauri-plugin-notification`** (its `NSUserNotification` backend is a silent no-op on macOS 26): `notify.rs::setup_banners` (authorize once; delegate returns `.banner`; guard on `!is_dev()`). Don't reintroduce the plugin for banners.
- **Every libghostty surface's render layer needs an OPAQUE background** or clicking a *cold* tab flashes the wallpaper for the pre-first-paint frames — `surface/ghostty.rs::new` (`#0e1516`, via a properly-typed `CGColor`). The `#empty-state` placeholder can't win that sub-frame race.
- **The render layer's `contentsScale` must track the backing scale** or the surface scales wrong across a DPI change — the lever is the *layer* scale, not the font path (it does reflow) and not a respawn; multi-monitor *refresh* is separate, via `ghostty_surface_set_display_id` — `surface/ghostty.rs::viewDidChangeBackingProperties` + the `windowDidChangeScreen:` observer.
- **App-menu shortcuts vs libghostty keybinds:** give the main menu first refusal at the top of `performKeyEquivalent:` or libghostty swallows the standard tab chords; `⌘\`` is reserved for macOS window-cycling (returned NO, never forwarded, or a Kitty-protocol TUI eats it) — `surface/ghostty.rs::performKeyEquivalent:`.
- **libghostty cursor focus must track AppKit's first responder** (else a clicked terminal types with a hollow cursor): a `becomeFirstResponder` override plus per-window `windowDidBecomeKey:`/`windowDidResignKey:` observers — which-surface-within-window vs which-window, both needed — `surface/ghostty.rs`.
- **Stale frontend embed:** `ui/` assets embed at compile time with no `rerun-if-changed`, so a frontend-only edit serves stale HTML until a Rust change forces a recompile — `build.rs` watches `ui/index.html` (add any new hand-written page; don't watch `ui/` broadly — build.rs writes generated files there). Symptom: "my HTML change didn't take" → touch a `.rs` or `cargo clean -p warden-app`.
- **Format-on-save must not loop the watcher:** the reload hook's `format_file` rewrites only on the **clean-parse branch** and only if bytes differ (diff-guard), atomically; formatting must stay **idempotent** so the guard converges (warden's own write retriggers once, then settles). The house style is single-sourced in config-core's `format_str` — `main.rs` reload hook + config-core `format_file`.
- **Tab reconcile shapes (identity by `id`-else-`dir`):** a kept tab's `title`/`group`/`probe`/`kill` change is a live relabel (`set_meta`, no respawn); a `dir`/`cmd`/`shell`/`load_on_open` change rides `respawn_tabs` (targeted in-place PTY respawn); changing `dir` with no `id` set changes the key → remove-old + add-new, not `respawn_tabs`. `reconcile.rs`/`resolve.rs`; identity scheme in [`docs/config.md`](docs/config.md).
- **The empty-state placeholder is an in-page element composited BEHIND the content**, shown only when no live surface covers the hole (`#empty-state` in `index.html`). It must stay **opaque** (the window is transparent — a non-opaque fill leaks the wallpaper, the exact leak it exists to stop) and lives in warden's shell, not chrome-core (a content-area concern; curator/lector do the same with their raised webview).
- **A hot-reload while the home surface shows a window list must reconcile, not re-materialize** ("closed windows reopen on save"): key the recovery branch on `last_good.windows.is_empty()`, not on zero real windows open — only a genuinely no-baseline state re-materializes. `main.rs` reload hook.
- **Every load-failure call site routes through `self.load_error` + `sync_empty_surface`** — never a direct `show_home`/`close_home` or a bespoke error window (a warden-local diagnostic window once did, making `NoConfig`/`Broken` unreachable). `home_state`'s precedence (real window → `NoConfig` → `Broken` → `Windows`) does the picking; a call site's only job is to keep `self.load_error` current. `manager.rs`.
- **Pop-out's backend invariants** (break one → deadlock, duplicate a tab, or drop a live PTY): 3-phase lock discipline — extract the surface under the `ManagerState` lock → build the detached window + `reparent` with the lock **RELEASED** → re-lock to store + wire the return; the `TabSlot::Detached` placeholder keeps hot-reload `reconcile` from duplicating the tab; `detached` is counted by `is_empty()`; the `is_quitting` guard in `redock` prevents mid-teardown resurrection; a live surface is dropped only when `redock` finds the origin gone from config. The origin sidebar renders a popped tab muted via the **forwarded** `detached` DTO field (clicking it calls `raise_popped_window`, not `activate_tab`). `main.rs::pop_out_tab` + `manager.rs::redock` + `registry.rs` (`detach`/`attach`).
- **Size the reparented surface's birth rect from the BUILT window, never from `DETACHED_DEFAULT_*`** — shell-core's geometry plugin restores this tab's remembered size *during* `open_detached`'s `build()` (its `on_window_ready` hook runs before `birth_content`), so the constants passed in are stale for every pop-out after the first and the surface lands visibly the wrong size until `detach.html` reports the true hole. `main.rs::pop_out_tab`'s birth closure reads `win.inner_size()`.

## Relationship to curator and lector (the shared chrome-core component)

warden, **curator** ([github.com/Lockyc/curator](https://github.com/Lockyc/curator)) — a sibling public macOS Tauri app that curates **browser keeper-tabs** (webviews) where warden curates **terminals** (libghostty surfaces) — and **lector** ([github.com/Lockyc/lector](https://github.com/Lockyc/lector)) — a sibling app that curates **local documentation sites** — share the same sidebar chrome, extracted into **chrome-core** ([github.com/Lockyc/chrome-core](https://github.com/Lockyc/chrome-core)). All three apps consume it, so a look/behaviour change is made once and all three move together.

- **The sidebar chrome IS chrome-core (the view) — change it there, not here.** chrome-core owns the banner + accent tint, grouped tab rows (letter tile, title, the three dot slots: attention / presence / live-unload), the kill-confirm row overlay, density tokens, the resize-drag, the error bar, and the **collapsible project-tree rendering** (`buildTree` + tree render: compressed single-child folder chains, expand/collapse state persisted in `localStorage`, a manual refresh control on the section header, an empty "No projects found" state) driven by each tab's `tree`/`treePath` DTO fields. It's a build-dependency pinned by `rev`; `build.rs` writes `SIDEBAR_CSS`/`SIDEBAR_JS` into `ui/chrome-core.{css,js}` (git-ignored) before `generate_context!` embeds them. `ui/index.html` is now a **page shell + thin controller**: the `#app`/`#terminal-hole`/empty-state topology, `reportRect`, the `forMe` per-window filter, the first-probe handshake, and a controller that maps the component's callbacks (`onSelect`→`activate_tab`, `onUnload`→`unload_tab`, `onKill`→`kill_session`, `onKillClose`→`kill_session` + `unload_tab`, `onStart`→`start_session`, `onRescan`→`rescan_root`, `onResize`→CSS width) and events (`warden:refresh`→`update`, `warden:notify`→`setAttention`, `warden:session-state`→`setPresence`, `warden:error*`→`setError`/`clearError`) to warden's backend.
- **What stays per-app is topology + backend, not the sidebar.** warden keeps its native-surface hole (`#terminal-hole` + `reportRect` + the empty-state placeholder) and its Tauri commands/events; curator keeps its content webviews + its own commands. These are the ~40-line controllers, not chrome duplication. warden feeds the component a normalized tab DTO where `presence` (probe), `killable` (kill), `startable` (has a `cmd` to restart a dead session), and `tree`/`treePath` (project-tree-roots sectioning) are warden-only — curator never sets them — and `attention` carries no count (curator's unread count does). warden also sets the window-level `windowDrag` flag (from its `sidebar_drag` config, default on) so the component makes the non-interactive chrome a `data-tauri-drag-region`; the component defaults it **on** when absent, so this is warden opting the toggle *in/out* rather than enabling a default-off feature. warden passes **no** `active` field, so the component owns selection (preserve + fall back to first, firing `onSelect` to activate); curator passes `active` because its Rust side is authoritative.
- **A new `TabDto` field is invisible to the chrome until `toComponentDto` forwards it (the "tree rendered flat" bug).** warden's Rust `TabDto` and the chrome-core component DTO are *separate shapes*; `ui/index.html`'s `toComponentDto` hand-maps one to the other. Adding a field to `TabDto` (Rust) is only half the wiring — if `toComponentDto` doesn't copy it across, the component simply never sees it, with no error. This is exactly how `tree`/`treePath` shipped inert: the Rust side emitted them and chrome-core rendered trees on `tree === true`, but the controller dropped both, so every `[[window.root]]` rendered as a flat group. When you add a component-facing tab field, add it to the `TabDto` struct **and** the `toComponentDto` mapping in the same change.
- **Dev iteration on the chrome behind a pinned rev is higher-friction — use the `chrome-*` just recipes** (they assume the sibling `../chrome-core` ghq checkout). **`just chrome-dev`** activates a normally-commented `[patch]` in the workspace `Cargo.toml` so warden builds against your local `../chrome-core` (uncommitted edits included); iterate, then **`just chrome-pin`** re-pins `crates/warden-app/Cargo.toml` to `../chrome-core`'s pushed HEAD and re-comments the patch. **config-core and shell-core have the mirror pairs** — **`just config-dev`** / **`just config-pin`** (re-pins `crates/warden-config/Cargo.toml`) and **`just shell-dev`** / **`just shell-pin`** (re-pins `crates/warden-app/Cargo.toml` — shell-core appears there twice, as a build-dep and a dep, and `shell-pin` re-pins both), since both are git-pinned the same way and hit the identical land-order footgun; the three cores use **scoped `#PATCH:chrome#` / `#PATCH:config#` / `#PATCH:shell#` sentinels** in the workspace `Cargo.toml` so each `*-dev` uncomments only its own patch. **Never commit an active patch** — a path patch builds green for you but is unresolvable for every clone/CI; **`just gate` refuses while any is active, and a `.githooks/pre-commit` guard blocks a commit that stages one** (the two safety nets). Edit chrome-core's `assets/sidebar.{css,js}` — never the generated `ui/chrome-core.*`. For **visual** tweaks, skip building warden entirely: chrome-core's checked-in **`preview.html`** renders the sidebar in isolation — **`just chrome-preview`** opens it (or `just preview` / `just shot` inside chrome-core), with `?density=compact` and `?header=1` (preview the nav-pill header slot + a live banner-height readout) URL params. See chrome-core's CLAUDE.md for the full loop.
- **Terminal-only vs browser-only affordances are DTO/callback differences, not ports.** A terminal has session state, so warden's unload *kills* the terminal (no cheap re-fetch, no curator-style reload-on-click). curator's browser nav (back/forward/home/reload) mounts into the component's optional `header` slot, which warden leaves null.

## Shared release tooling + Tauri runtime: `shell-core`

The third shared core (`https://github.com/Lockyc/shell-core`), alongside chrome-core and config-core,
consumed by git-rev pin. It owns the build/release tooling and the byte-identical sliver of Tauri setup
that is the same for warden, curator, lector, and any future sibling app.

- **Release scripts are generated, not tracked.** `crates/warden-app/build.rs` calls
  `shell_core::materialize_scripts("../../scripts")`, writing `scripts/{release,gen-latest-json,install-app}.sh`
  **git-ignored** from the pinned rev. The generic scripts read the tracked `scripts/tooling.env`
  (`APP_NAME`/`TAURI_CRATE_DIR`/`UPDATER_REPO`); everything else derives. **Edit them in shell-core**, never
  here — the local copy is overwritten on the next build. So warden, curator, and lector all run **one**
  shared release script (the `scripts/release.sh` mentions above and under *Releases* resolve to that generated file).
- **The build stamp comes from shell-core.** `build.rs` calls `shell_core::build_stamp()`, emitting
  `BUILD_GIT_SHA`/`BUILD_DATE`; the app-menu About item reads them via `env!` (warden previously had no
  build stamp — this closed the asymmetry with curator).
- **The menu spine and the home surface come from shell-core** (`menu::build_spine` /
  `home::{home_state, show_home, close_home}`, both behind the `runtime` feature). `build_app_menu`
  calls `build_spine` for the App/Config/Window submenus and composes warden's own Tab submenu
  around them — `shell_core::menu::build_tab_nav`'s digit-mode items, the spine's `Close Tab`/
  `Pop Out Tab`, and Reopen Last Closed (⌘⇧T, warden-only — see *App menu* above) spliced into the
  Window submenu. The home surface **replaces both of warden's former single-purpose
  windows** — `manager.rs`'s old `show_launcher`/`close_launcher`/`refresh_launcher`/`LAUNCHER_LABEL`
  + `ui/launcher.html`, and later its `show_diagnostic`/`clear_diagnostic`/`DIAG_LABEL`/
  `diagnostic_msg` + `ui/diagnostic.html` (the diagnostic was carried past the first cutover,
  reasoned as "warden-specific" — wrongly, see *Persistence & empty states* above), are all
  deleted, not kept alongside the shared one. `sync_empty_surface` is the single authority,
  calling `shell_core::home::{home_state, show_home, close_home}` for every state
  (`NoConfig`/`Broken`/`Windows`) — no app-side error window of any kind. **The quit-on-close
  behaviour is kept and re-attached, not dropped**: shell-core's `show_home` installs no
  window-event handler of its own (curator and lector need none — plain last-window-quit already
  covers them), but warden's former launcher always quit the app when *it* was the last surface
  closed — `sync_empty_surface` re-installs that `Destroyed` handler on the home window the first
  time it's actually built (idempotent `show_home` refreshes on subsequent calls, so the handler
  is attached once, not re-attached on every refresh), and it now covers all three states, not
  just the window-list one the old launcher had. The surface's "Create a starter config" button is
  warden's own `shell_home_create_config` command, calling `config_core::write_default_config`
  with warden's own `src/default-config.toml` template — shell-core never touches config-core (the
  three cores stay mutually independent; see the constellation `CLAUDE.md`).
- **Plugin registration, including window geometry persistence, comes from shell-core.** `main.rs`
  registers the geometry plugin + updater + process via
  `shell_core::register_plugins(builder, Some(&config_path), &[])`, passing warden's resolved config
  path — shell-core derives the per-config geometry-store filename from it (`geometry_filename`, its
  own `fnv1a_64`), so the canonicalize→hash→format policy is single-sourced there, not per app (only
  the *path* is app-specific). Geometry is persisted in AppKit points and clamped to the target
  monitor's work area on restore, and restore/save both run entirely inside the plugin (its own
  `on_window_ready` hook, which fires for runtime-built windows too) — warden triggers none of it by
  hand (see the FOOTGUN in `manager.rs::build_window`). **That covers a popped-out tab's window
  too** — keyed by its `shell-detach:` label, which `plan::detach_window_token` derives
  deterministically from `origin_label:tab_key`, so a re-popped tab reopens at the size and
  position it was last left at rather than the `DETACHED_DEFAULT_*` size. Only the shared home
  surface is excluded structurally by the plugin, so `skip_labels` is empty here;
  it's reserved for an app's own transient windows, which warden has none of today. The `runtime`
  feature pulls tauri; the `build.rs` build-dep uses `default-features = false` so it stays zero-tauri
  (resolver 2 keeps the two separate).
- **Not shared (genuinely warden-specific):** IPC fan-out (warden inlines `emit_to` with
  app-namespaced `warden:refresh` events + a `forMe()` filter); **warden's own config watcher** (it
  parses inside + drives a slow root-scan/main-thread reconcile and relies on `format_file`'s
  diff-guard — curator + lector share `shell_core::watch`, but warden's contract is different, and
  its file-name match is the reference that shared watcher was modelled on); and warden's own **Tab
  submenu items** (digit-mode jumps, Reopen Last Closed) — genuinely warden-specific, unlike the spine
  that now wraps them. warden has **no** chrome-caller command gate — not because "only curator hosts
  untrusted content" (the gate is redundant vs remote anyway; origin dispatch handles that — see
  shell-core's command-isolation model), but because warden's surfaces are native `NSView`s with no
  webview to spoof a call and no second local surface to screen. See shell-core's CLAUDE.md for the full dividing
  line.
- Dev loop: **`just shell-dev`** / **`just shell-pin`** (rev in `crates/warden-app/Cargo.toml`, scoped
  `#PATCH:shell#`), mirroring the chrome-/config- pairs.
- **Follow-up — a scriptable "open window by title" entry point belongs here (shared).** Nothing outside the
  app can open/raise a specific window today: it's GUI-only (Window menu, the home surface's window list,
  notification), and a second `open -a warden --args …` is silently dropped — there's no
  `tauri-plugin-single-instance`, `tauri-plugin-deep-link`, or CLI-arg handling. Build the entry point **in
  shell-core** so warden, curator, and future siblings inherit one implementation (same shape as
  `register_plugins`): single-instance argv (`--window <title>`) or a `<scheme>://window/<title>` deep link,
  forwarded to the already-running instance and mapped title → open-or-focus. Driver: a window configured
  `open_on_start = false` can't be opened by a login script, a shortcut, or any other automation today —
  only by hand from the home surface or the Window menu. This closes that gap.
