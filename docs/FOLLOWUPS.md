# warden — deferred follow-ups

Known, intentionally-deferred work. Each item is a conscious deferral, not an oversight — recorded here so it isn't lost. Remove an item when it's done.

## To add in `warden-app` when needed

These are trivial, zero-retrofit additions to make the moment `warden-app` needs them; deferred per YAGNI.

- **Make `auto_update` hot-reloadable** (`main.rs` reload hook + `ui/index.html`). Today the flag is read once at init and chrome-core arms its launch + 6h checks from it then, so toggling `auto_update` is restart-only (see the *In-app updates* bullet in `CLAUDE.md`). Wiring it into the reload hook — re-arming chrome-core's checks the way `density`/`probe_interval` already re-run on save — would make the toggle take effect live. Deferred per YAGNI: the update toggle is rarely flipped, so a restart is acceptable. Revisit if live toggling is ever wanted.

- **Add `serde` derives to the model types** (`Config`, `Window`, `Tab`, `Warning`, `Colour`) — only if a future slice chooses IPC-direct model types over the app's own DTOs. `warden-app` deliberately maps `Window`/`Tab` → app DTOs (web contract decoupled from the model), so this stays deferred. Tauri IPC `#[command]` return types must be `Serialize` to cross to the web chrome. `serde` is already a dependency — add the `derive`/`serialize` feature and the derives when the IPC layer lands, rather than maintaining parallel DTOs.

## Watcher robustness (deferred to `warden-app`)

- **No debounce / coalescing** in `Watcher` (`crates/warden-config/src/watch.rs`). The callback fires for every filesystem event matching the config file name. Editors that write in place (rather than atomic temp-file + rename) can produce a transient `load()` parse error (a partial read mid-write) and/or multiple callbacks per save. Atomic-save editors are unaffected. Debounce/coalescing is intentionally left to `warden-app`, which owns the reload UX and already keeps last-good config on a parse error. Also documented at the call site.

## Chrome (`ui/index.html`) has no automated test coverage — deferred, not forgotten

`ui/index.html`'s DTO-mapping and event-filtering logic (`toComponentDto`, `forMe`, the `warden:session-state` handler) has zero committed tests — no unit harness, no e2e, in any of warden/chrome-core/curator. This has already bitten the same bug class twice on the 3-state-presence branch: `toComponentDto` once coerced the (now-string) `t.presence` back to a boolean, painting every non-`"off"` tab live cyan; and a brief's snippet nearly shipped `forMe(e.payload)` (passing the payload instead of the event), which would have made the per-window filter always return `true` and silently stop filtering. Neither is catchable by the compiler (plain JS) or by any Rust/Cargo test — the failure lives entirely in `ui/index.html`'s hand-written DOM/event glue.

A throwaway harness proved a fix is viable: headless Chromium over CDP, with a stubbed `window.__TAURI__` bridge, loading the real `index.html` + the real generated `chrome-core.js`, asserting the presence-state → dot-class mapping (8/8 cases). It was built to verify this branch's fix, then deleted — nothing tracks the approach or the gap it closed. **Deferred, not committed to:** stand up that CDP harness (stubbed Tauri bridge + real chrome assets) as a real test target if this bug class bites a third time, or before the next chrome-touching DTO change.

## warden ↔ agentmux signal richness (deferred integration ideas)

Two related deferrals about the seam between warden and agentmux. Both are conscious decisions, not gaps.

- **Richer agent-state channel (deferred).** Today warden receives only two coarse signals per tab: an undifferentiated **amber attention badge** (OSC 777, fired by agentmux on both *permission-needed* and *done*, collapsed into one indicator) and a **presence dot** (three states, from the probe's exit code — see `docs/config.md`). agentmux itself already computes distinct per-agent states — *working / needs-permission / waiting / done*. A future protocol addition (a richer escape carrying the state, or a structured presence channel) could let warden render "needs-you" **distinctly** from "done" instead of one amber dot for both. **Caveat to keep in mind before "fixing" this:** the mapping is **inherently lossy regardless of protocol richness** — many agentmux tabs (tmux windows) map onto a *single* warden tab (one libghostty terminal surface), so a warden tab necessarily aggregates N agents' states into one indicator. This N→1 collapse is structural, not a bug: don't later mistake the aggregation for something to "fix" by trying to surface per-agent state on a single terminal surface. **Second caveat — same cold-start limit as presence (below):** a pushed state channel is edge-triggered, so it can only ever drive *live* attention (a badge as a transition happens); it can't be the authority for "what state is each agent in right now" when the client just reopened. The poll-based presence dot stays the cold-start source of truth; any state channel enriches the live view on top of it, it doesn't replace the baseline.

- **Presence stays poll-based, by decision (not push).** We considered replacing warden's per-tab `amux --probe` polling with an **agentmux-pushed presence escape** (an OSC the agent emits on session start/stop) — lower latency, no periodic `sh -c` overhead. **Decision: keep polling**, for two reasons, the first decisive:
  1. **Correctness on cold start — push is edge-triggered, poll is level-triggered.** A pushed presence escape only announces *changes*. Reopen the warden client (or restart it, or recover from a crash) and it begins with a blank slate: every amux session that came up *before* the client existed was never announced, so every presence dot sits dark until the user visits each tab — you can't tell which projects have live sessions without exploring all of them. Polling re-derives current truth on every interval, on focus, and on hot-reload, so a freshly-opened warden lights the right dots within one pass, untouched. This is the property that makes reconnect work at all; a pure-push model **cannot** provide it.
  2. **Generic seam.** Polling also keeps warden **tool-agnostic** — it reads only a probe command's *exit code* and encodes nothing about amux/tmux/sockets/naming (the command is entirely the user's; see the probe footguns in `CLAUDE.md`). A pushed escape would bake an agentmux-specific signal into warden's core.
  Recorded as a **settled decision** so a future "optimize poll → push" isn't re-litigated. If push is ever added it must be an **augmentation on top of poll** (poll remains the cold-start source of truth; push only lowers live-change latency) — **never a replacement**.

## Release signing — optionally source the updater-key password from the macOS Keychain

`just release` (`scripts/release.sh`) needs two updater-signing env vars beside the Apple creds: `TAURI_SIGNING_PRIVATE_KEY` (the contents/path of `~/.tauri/warden-updater.key`, which lives on disk mode-600) and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Both must be present in the build env before `just release` runs — however a maintainer chooses to hold and inject that passphrase, it's a manual step today.

**Intended change:** let the release path optionally read the updater-key password from the **macOS Keychain** (a generic password item), non-interactively — `security find-generic-password -s warden-updater-key -w` — so `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` can be populated the same way `APPLE_PASSWORD` is already sourced for notarization, with no manual export. Fall back to the env var when the Keychain item is absent, so a contributor without one isn't blocked. **Wire it into shell-core's generic `release.sh`, not warden's** — warden's `scripts/release.sh` is materialized from the pinned shell-core crate at build time and git-ignored, so an edit to the local copy is overwritten on the next build.

## Shared-core dev loop — `just <core>-dev` can silently build against the *pinned* rev

`just chrome-pin` ends with a `cargo update -p chrome-core`; **`just chrome-dev` has no equivalent** — it only uncomments the `#PATCH:chrome#` sentinel lines. With a stale lockfile, Cargo then drops the path override to `[[patch.unused]]` and **still builds green**, emitting only a build-log warning. The failure shape is the dangerous one: `just chrome-dev && just run` tells you warden is building against your live `../chrome-core` checkout while the binary actually carries the **pinned** rev — so you "verify" a change that isn't in the app. Caught during the kill-both work only because the new symbol was grep-ably absent from the generated `ui/chrome-core.js`; a *visual* tweak would have produced a silent false negative (you'd see the old sidebar and conclude your CSS was wrong).

**Intended change:** add `cargo update -p chrome-core` to `chrome-dev`, mirroring what `chrome-pin` already does — and to its `config-dev` / `shell-dev` twins, which share the shape. Cheap and mechanical; the value is that the dev loop stops lying about what it built. While there: `chrome-pin`'s clean-tree precondition on the sibling checkout blocks the recipe outright when that repo has *any* unrelated dirty file (it only needs `assets/` clean to be meaningful) — consider scoping the check to the paths the pin actually depends on.

## Release manifest — stamp `pub_date` into `latest.json`

`scripts/gen-latest-json.sh` emits the updater manifest without a `pub_date` field, so every release's `latest.json` ships without one (confirmed on v0.6.1). The `tauri-plugin-updater` client does **not** require it — updates work fine without it — so this is cosmetic: `pub_date` only surfaces as update metadata (e.g. a "released on" line a UI could show). Adding it is a one-liner in the generator, which already runs on the release machine where `date` is available: stamp an RFC 3339 UTC timestamp (`date -u +%Y-%m-%dT%H:%M:%SZ`) into the JSON's top-level `pub_date`. **Make the change in shell-core and re-pin** — warden's `scripts/gen-latest-json.sh` is materialized from the pinned shell-core crate at build time and git-ignored, so a local edit is overwritten on the next build. Low priority; do it if a future update UI wants to show the release date.

## Project-tree roots (`[[window.root]]`) — deferred

- **Live filesystem watcher for roots.** Rescanning currently happens on window open, on every config hot-reload, and via the manual refresh control (`rescan_root`) — there is no `notify`-based watch on a root's `dir`, so a project cloned or removed on disk doesn't surface until one of those triggers fires. Would mirror `crates/warden-config/src/watch.rs`'s approach, scoped per root.
- **Root scan runs on the main thread (no longer under the lock).** `rescan_root` and the hot-reload reconcile branch (`main.rs`) call `effective_config` → `scanner::synthesize_tabs` → config-core's `discover_projects`/`scan_root` (a filesystem walk) on the main thread, so a rescan of a very large/deep tree briefly stalls the UI. The scan is now lifted **out of the `ManagerState` lock** — `rescan_root` clones `raw_config` under a brief lock then scans lock-free, and the hot-reload branch scans before locking, both re-locking only to `apply` (safe because both run on the main thread, so no writer interleaves) — mirroring how the probe path releases the lock before slow `sh -c` calls, so a scan no longer blocks the probe poll thread. The **remaining** main-thread stall is inherent: reconcile/`apply` build windows, which must run on the main thread, and is bounded by config-core's `DEFAULT_ROOT_DEPTH`. A true fix would need async materialization; deferred pending real-world evidence it matters.
- **Non-`.git` project markers.** config-core's scanner (`scan_root`, shared with lector) only recognizes a `.git` dir or file. Other project markers (`.hg`, `.jj`, a `package.json`/`Cargo.toml` at a dir's root, etc.) aren't discovered. Revisit if a non-git workflow needs auto-discovery.
- **Per-discovered-project config overrides.** A discovered project has no per-tab config level (root → window → global only) — there's no way to override `shell`/`cmd`/`probe`/`kill`, exclude one project, or pin a `load_on_open` for a single discovered tab without promoting it to a curated `[[window.tab]]`. An override map keyed by path (or a per-root exclude list) would close this; deferred until a real need shows up.
- **Nested roots / a root inside a group.** `[[window.root]]` currently sits at the window level only, alongside loose tabs and `[[window.group]]`s. A root scoped inside a `[[window.group]]` (so discovered projects nest under an existing group's section) or a root whose scan itself contains another declared root are both unimplemented.
- **Overlapping roots: dedup by key keeps the first, group-precedence is first-root-wins.** `effective_config` (`manager.rs`) dedups discovered tabs by `key` (absolute path), keeping the first occurrence — so two roots whose `dir`s overlap surface the shared project **once**, under the first root's section (file order). This is deliberate: a duplicate key isn't just a doubled row, it causes perpetual `set_meta` churn (reconcile matches find-first, so the second copy never settles). What's *not* handled: choosing *which* root a shared project belongs to beyond "first wins" (e.g. a per-root exclude, or nesting the project under the more-specific root) — deferred until a real need shows up. A curated `[[window.tab]]` pointing at a dir a root also discovers still produces two rows (different keys — title vs path), which is left as-is (promote to a curated tab or don't overlap).

## Native splits — a click on a LIVE pane doesn't sync `Registry.focused` (Task 7)

`ui/index.html`'s per-pane `mousedown` handler (`focusPane`, bound on `#pane-primary`/`#pane-secondary`) is the only thing that calls the `focus_pane` command, which is the only thing that updates `Registry`'s own `t.focused` (consulted by `activate`'s re-focus branch on a later tab switch). But a LIVE pane's terminal content is a separate native `NSView` composited **above** the webview (see `CLAUDE.md`'s module header), so a click that lands there is consumed by AppKit — `WardenHostView::becomeFirstResponder` (`surface/ghostty.rs`) — before it ever reaches the DOM. That already moves KEYBOARD focus correctly (typing lands in the clicked pane, because `becomeFirstResponder` is the real first-responder hook), but it does **not** call back into `Registry.focused`. Net effect: switching away from a split tab and back can restore focus to the wrong pane, specifically when the user's last click on that tab was directly on an already-live pane's content rather than on a cold pane or the chrome-only margin around it.

**Intended fix:** route `WardenHostView::becomeFirstResponder` through the same surface→tab lookup `notify.rs` already uses for bell/notification signals (`Registry::locate_surface` → `focus_pane`), and emit a lightweight event so the chrome's `focusedPaneById`/`updateFocusMarker` mirror stays in sync with a native click too — not just chrome-driven ones. Deferred out of Task 7 (commands + menu item) because it touches a different subsystem (`surface/ghostty.rs`'s AppKit callback + a new surface-id→tab-focus routing path, mirroring `notify::init`) rather than extending the split/close/focus commands themselves. Verify by hand until then: click directly on a live secondary's content (not the empty-state backstop), switch tabs away and back, and check whether focus/the marker followed.

## `warden-app` surface-embed hardening

`crates/warden-app` embeds libghostty terminal surfaces in Tauri on macOS. The following hardening is deferred, by priority:

- **Make the `TerminalSurface` seam object-safe.** `close(self)` is by-value, so `Box<dyn TerminalSurface>` is impossible and the registry stores the concrete `GhosttySurface` — compile-time backend swap only, not runtime polymorphism (can't hold heterogeneous surfaces). Move to `close(&mut self)` to make it object-safe (the `Drop` path already owns teardown, below). The **drop-without-close leak is already guarded**: `GhosttySurface` has a `Drop` impl sharing an idempotent `teardown()` with `close()` — via a `closed` flag so neither path double-frees the libghostty surface or double-removes the observer — so a surface dropped without `close` no longer leaks the surface/PTY or leaves a dangling notification observer. (Drop was prioritized as a leak, not a UAF: selector-based observers are zeroing-weak on the macOS 11+ target and the host view's `surface` ivar is null/stale so its handlers early-return; the guard closes the leak regardless.)
- **Finish `cfg(macos)` gating for an eventual Linux port.** The misleading-cross-platform-scaffolding problem is resolved: `surface/mod.rs:9` now gates `pub mod ghostty;` behind `cfg(target_os = "macos")`, and a non-macOS build fails honestly and immediately via `main.rs`'s `#[cfg(not(target_os = "macos"))] compile_error!(...)` rather than a confusing "can't find crate `objc2`". What remains for an *actual* Linux backend: `mod ffi;`/`mod surface;` in `main.rs` are still ungated (moot today behind the `compile_error!`), so when Linux work starts they (and the `ffi`/`objc2` deps) need gating alongside removing the `compile_error!`. Mechanical; do when Linux work starts.
- **`Registry::new` takes a raw `*mut c_void` NSWindow pointer** (`registry.rs`) — the registry interface is itself platform-aware, so a non-macOS backend can't implement it without knowing what the pointer means. Pass a platform-opaque handle or a surface-factory closure so the registry stays platform-agnostic (the seam's intent).
- **Move libghostty lifecycle init behind the seam.** `ffi::ghostty_init` is still called from `main.rs`; the surface layer should own libghostty init so `main.rs` never names libghostty (the seam constraint).
- **Terminal input — remaining gaps.** Wired (`surface/ghostty.rs`): control-key encoding (`is_printable_text` keeps control chars out of `text` so legacy apps get bare control bytes, not Kitty `CSI…u`), ⌘-combos (`performKeyEquivalent:` forwards to libghostty's bindings — ⌘-presses arrive there, *not* `keyDown:`), mouse button/drag/scroll, **mouse motion** (`mouseMoved`/`mouseExited` via an `NSTrackingArea`, which is what lets libghostty resolve the cell under the cursor → link hover), and copy/paste (clipboard callbacks ↔ `NSPasteboard`, routed to the focused surface via `FOCUSED_SURFACE`). Still unhandled: **Alt/Meta** combos (Option yields the macOS composed char as text rather than an ESC-prefixed Meta sequence), **function/arrow/nav keys** (no explicit encoding — whatever libghostty derives from `keycode`), and **IME / dead keys / marked text** (no `NSTextInputClient`).
- **Full keybindings + ad-hoc tabs.** Tab navigation is wired as **menu items** (the macOS-native, focus-independent path): a **Tab** submenu with **Previous Tab ⌘⇧[ / Next Tab ⌘⇧]** and digit chords whose binding follows the global `tab_digit_keys` config (`"jump"` default → **⌘1–⌘9** jump-to-position; `"cycle"` → **⌘1 / ⌘2** next/prev + **⌘3–⌘9** jump), plus an app submenu with **About / Check for Updates… / Minimize ⌘M / Close Window ⌘⇧W / Quit ⌘Q** (all in `main.rs` setup) — note **⌘W is Close Tab**, in the Tab submenu, not a window close. Items fire the Builder's `on_menu_event`, which `emit_to`s the focused window (`warden:cycle-tab` ±1 / `warden:select-tab` n); the chrome reuses `select()`. We deliberately did **not** use ⌘+arrow — it collides with macOS line/document text-nav and could only be captured per-view (focus-dependent, fighting the OS); the menu is checked app-wide before any view. Window cycling (**`cmd+\``**) is **macOS's own** and needs nothing from warden but *not eating it*: `performKeyEquivalent:` reserves the chord from libghostty (returns `NO` without forwarding, so AppKit cycles — see the menu-vs-keybind footgun in `CLAUDE.md`). It is **not** a deferred warden feature — warden owning its own cmd+` would mean fighting the OS. Still deferred: **ad-hoc tabs/windows** (`cmd+T`/`cmd+N`).
- **libghostty actions warden still ignores (a conscious set, not an oversight).** Handled today (`surface/ghostty.rs::action_cb`): `RING_BELL` + `DESKTOP_NOTIFICATION` (→ attention badge / macOS banner), `SHOW_CHILD_EXITED` (→ unload the dead tab to cold), `OPEN_URL` + `MOUSE_SHAPE` (→ clickable links). Deliberately **not** handled (a standing invariant, not a deferral): the tab/split/window family (`NEW_TAB`, `NEW_SPLIT`, `CLOSE_WINDOW`, `GOTO_TAB`, `TOGGLE_FULLSCREEN`, …) — warden owns its window/tab set (from config, plus its own config-less classes), so the embedded terminal must never create or destroy them. This constrains **libghostty**, not warden: pop-out (⌘⇧O, `main.rs::pop_out_tab`) is a config-less window warden mints itself today, and ad-hoc `⌘T`/`⌘N` (deferred above) would land the same way — warden creating a config-less surface, *not* warden handling libghostty's `NEW_TAB`. So the invariant doesn't block `⌘T`; it just fixes the trigger as warden, never the terminal. Genuinely open, in rough value order: **`PROGRESS_REPORT`** (OSC 9;4) and **`COMMAND_FINISHED`** (shell-integration-driven, so it only started firing once warden began shipping libghostty's resources) — both are natural sidebar signals for a background agent tab, but need a design call on what a row shows; **in-terminal search** (`START_SEARCH`/`SEARCH_TOTAL`/`END_SEARCH`), which needs new chrome UI; and **`SET_TITLE`/`PWD`**, which warden currently overrides with its config-declared titles by design.
- **FFI hardening.** C-populated `#[repr(C)] enum` fields in `ffi/mod.rs` (`platform_tag`/`backend`/`context`) risk invalid-discriminant UB if libghostty ever returns an unknown value — note the UB triggers the instant `ghostty_surface_config_new()` returns the struct **by value** (in `GhosttySurface::new`, `surface/ghostty.rs`) and Rust materializes those enum fields from C bytes, before any field is overwritten; use integer newtypes (as already done for `mods`). The `size_of` asserts guard total size, not field offsets.
- **Pin the "libghostty copies strings during the call" assumption.** Correctness of `ghostty_surface_new` (and `ghostty_app_new`) depends on libghostty copying the config strings (`working_directory`/`command`) and the runtime config *synchronously during the call* — they're stack locals (in `GhosttySurface::new`, `surface/ghostty.rs`) that die on return. Almost certainly true (matches Ghostty's macOS app), but unverified against the header and currently the single most consequential unchecked invariant: a future lib/header bump that retained the pointers would be a silent UAF. Verify against the Ghostty source at the pinned commit (`vendor/PROVENANCE.md`); consider a defensive comment/test at the call site.
- **Tighten the IPC boundary (CSP hardening).** A restrictive CSP **is now set** (`tauri.conf.json`): `default-src 'self'`, `object-src 'none'`, `frame-src 'none'`, `base-uri 'self'`, `img-src 'self' data:`, `connect-src 'self' ipc: http://ipc.localhost`. It still allows **`'unsafe-inline'`** for `script-src`/`style-src` because `index.html`'s `<script>`/`<style>` are inline — so the CSP blocks remote loads but not inline injection. Config colour still reaches the DOM (`index.html` sets the sidebar background from the window colour via `tintOverBase(windowColour, …)`), but only as a config-core `Colour`-validated hex composited into a `style.background` value, so it isn't an open sink today. Residual hardening: externalize or nonce the inline `<script>`/`<style>` and drop `'unsafe-inline'`, and revisit `withGlobalTauri: true` (the full IPC bridge is exposed to the renderer). `set_hole_rect`'s f64-rect validation is also done (`main.rs` rejects non-finite + clamps to ±100k before converting).
- **Packaging now signs + notarizes; a `.dmg` target is the residual.** Release `just build`/`just deploy` produce a `warden.app` that **is now signed with Developer ID and notarized + stapled** when the Apple signing/notary env vars are set (`APPLE_SIGNING_IDENTITY` pointing at a Developer ID Application cert, plus `APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID`, or `APPLE_API_KEY*`); Tauri runs the signing and `xcrun notarytool` submission during `cargo tauri build`. With those vars unset the build is ad-hoc/unsigned and `scripts/install-app.sh` strips the Gatekeeper quarantine xattr so a local copy runs. Releases currently attach a zipped `.app`; the only residual nicety is a **`.dmg` bundle target** (a draggable installer vs a zip), add one if wanted. (The `macos-private-api` item below independently bars the Mac App Store route.)
- **`macos-private-api` is now enabled** (`Cargo.toml` / `tauri.conf.json`) because windows are built at runtime and `WebviewWindowBuilder::transparent` is gated behind that feature on macOS. This uses private AppKit API, so it **bars Mac App Store distribution** — fine for the current direct-distribution target, but revisit if MAS shipping is ever wanted (would need a non-private transparency route or an opaque-window design).
- **Global `open_on_start` default (cascading window default).** `open_on_start` is a per-`[[window]]` flag only (default true, no cascade) — there's no global toggle to flip the default so individual windows opt *in* via `open_on_start = true` instead of opting out. Per-window control already covers the "some windows start closed" need; a global default is deferred until an "open nothing by default, opt windows in" workflow is actually wanted.
- **Decide ghostty argv passthrough.** `main.rs` (the `ghostty_init` block in `main`) forwards the full process `std::env::args()` into `ghostty_init`, so any ghostty CLI flag is injectable via warden's own argv. Decide: support passthrough (keep) vs pass a fixed `["warden"]` argv (recommended unless passthrough is a wanted feature). Also: those argv `CString` pointers are cast `*const`→`*mut c_char` for `char**` — verify ghostty treats argv as read-only, else hand it owned mutable buffers.
